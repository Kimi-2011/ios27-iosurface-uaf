# com.apple.kernel：27.2 修掉的一次「未受上界约束的写入」

> 来源：`out/patches/com_apple_kernel.md` 的「新增断言（udf/brk）」强信号
> 函数对 `0xfffffe000ab6b660` → `0xfffffe000abbb654`（208 B → 232 B）。
> 本文件是全项目第一个**形态明确的内存安全修补**。确定度分级标注。

## 1. 两版反汇编（原文，未改写）

### 27.0.1 `0xfffffe000ab6b660`

```asm
b6b6b4  ldr  w8,  [x9, #8]          ; w8 = 容器里的计数
b6b6b8  cbz  w8,  ret3              ; 计数为 0 -> 返回 3
b6b6bc  lsl  x11, x8, #4            ; x11 = 计数 << 4   （元素 16 字节）
b6b6c0  add  x12, x11, #0x10        ; x12 = 计数*16 + 16  （再放一个需要的空间）
b6b6c4  cmp  x11, w11, sxtw         ; 只检查 x11 是否超出 31 位（溢出检查）
b6b6c8  add  x13, x9, w11, sxtw     ; x13 = x9 + 计数*16   ← 指向 slot[计数]
b6b6cc  add  x16, x9, x11
b6b6d0  movk x16, #0x2bad, lsl #48  ; 毒化
b6b6d4  csel x13, x13, x16, eq      ; 溢出时 x13 = 毒化指针
b6b6d8  cmp  x12, x10               ; x10 = 容量上限
b6b6dc  csel x10, xzr, x13, hi      ; 空间不足时 x10 = 0
b6b6e0  ldr  w11, [x10, #8]         ; ★ 从 x10 读（不足时 = 读地址 0x8）
b6b6e4  str  w11, [x9, #8]
b6b6e8  str  w1,  [x10, #8]         ; ★ 写 x10+8（不足时 = 写地址 0x8）
b6b6ec  orr  x9,  x3, x2
b6b6f0  str  x9,  [x13]             ; ★★ 写 slot[计数]，完全不受上面的空间检查约束
```

### 27.2 `0xfffffe000abbb654`

```asm
bbb6b0  lsl  x11, x8, #4
bbb6b4  add  x12, x11, #0x10
bbb6b8  cmp  x12, x10               ; ★ 检查提前
bbb6bc  b.hi out718                 ; ★ 空间不足 -> 直接跳出，什么都不写
bbb6c0  cmp  x11, w11, sxtw
bbb6c4  add  x10, x9, w11, sxtw     ; ★ 目标地址改存进 x10
bbb6c8  add  x16, x9, x11
bbb6cc  movk x16, #0x2bad, lsl #48
bbb6d0  csel x10, x10, x16, eq
bbb6d4  cbz  x10, out720            ; ★ 二次检查
bbb6d8  ldr  w11, [x10, #8]
bbb6dc  str  w11, [x9, #8]
bbb6e0  str  w1,  [x10, #8]
bbb6e4  orr  x9,  x3, x2
bbb6e8  str  x9,  [x10]             ; ★ 改用受检的 x10，不再用 x13
```

## 2. 差别（这是确定的部分）

| | 27.0.1 | 27.2 |
|---|---|---|
| 空间检查时机 | 算完但**只影响 x10** | **提前，`b.hi` 直接跳出** |
| 最终写入地址 | **`x13`（未经空间检查）** | **`x10`（受检）** |
| 空间不足时 | 仍写 `slot[计数]`（越界）+ 写地址 `0x8` | 不写 |

**语义**：`x13 = x9 + 计数*16` 指向 **slot[计数]**，也就是「最后一个有效槽之后一格」。
空间足够时这是合法的「追加」；**空间不足时 27.0.1 仍然写这一格 ⇒ 堆越界写，写入量 16 字节，
内容是 `x9 = x3 | x2`（函数入参）。**

## 3. 函数形态推断（中等置信）

```asm
ldrb w8, [x0, #1]           ; x0 对象，偏移 +1 是标志字节
tst  w8, #7                 ; 三个标志位全清则走另一条路
ldr  x16, [x17, #0x68]!     ; 对象 +0x68 的指针
movk x17, #0xb9dc, lsl #48  ; PAC 多样性常量
autda x16, x17              ; 认证
```

- `autda` + 多样性常量 ⇒ **这是带 PAC 的类指针**，`+0x68` 是容器描述符
- `and x9, x16, #0xffffffffffffc000` / `orr x9, x9, #0x400000000000` /
  `and x11, x16, #0xf` / `lsl x10, x10, x11` ⇒ **对认证后的指针做位域解码**
  （低 4 位当移位量，bit 4 选择两种模式）——**不是直接使用**

⇒ **推断为一个带内联/压缩指针编码的容器（哈希桶或小型映射），
`ldr w8,[x9,#8]` 是元素计数，`str x9,[x13]` 是「追加到 slot[计数]」。**

**置信度**：中等。`slot[计数]` 的读法由 `lsl #4`（16 字节元素）+ `add #0x10`（再留一格空间）
两条指令直接支撑，不是猜的。

## 4. 可达性（已查，未定论）

```
0xab6b660 (27.0.1) 的引用: 1 个  BL 0xab72ac8
   -> 函数 0xab721b8  （无字符串）
   -> 调用者 0xab691c8 -> 函数 0xab68e0c（无字符串）
   -> 再往上：无直接调用者
```

字符串扫描已增强（`adrp`+`add` 直取 **和** `adrp`+`ldr` 经字面池间接取），
三层函数**仍然全部无字符串引用**。

⇒ **静态无法定性子系统。**

## 5. 可利用性：未证，三条未知

1. **`w8`（计数）是否可由用户态推到「已满」** —— 若能，越界写可稳定触发
2. **`x13` 越界之后的目标是否可控** —— 越界量固定为 +16 字节（恰好一格），
   不是任意偏移，可利用性取决于相邻分配布局
3. **`x2`/`x3`（写入内容 `x9 = x3|x2`）是否用户可控** —— 若可控，是「受控值写固定越界偏移」

**三条里任何一条不成立，这条就只是 DoS。** 必须逐条验，不能把形态当成果。

# ★ 后续：子系统已定位 = Mach IPC 端口（2026-11-01 18:2x）

## 8. 决定性对应：这就是 CVE-2026-112507

`out/ADVISORY-iOS-27.2.md` 第 72 行：

```
| Kernel | An app may be able to cause unexpected system termination or write kernel memory
         | 边界检查 | CVE-2026-112507 |
```

- 「**write kernel memory**」←→ 我找到的 `str x9, [x13]` 未受上界约束
- 「**边界检查**」←→ 27.2 加的 `cmp x12,x10` + `b.hi` + `cbz x10`
- 「**An app may be able to**」←→ Apple 认定 app 可达

**三者全对。置信度：高。**

## 9. 子系统定位过程（数据锚点法）

调用者 `0xab721b8` 里有一段表索引：

```asm
ldrb w8, [x22]              ; 对象 +0 的一个字节
cmp  x8, #0x32              ; < 50
b.hs out
add  x8, x8, x8, lsl #2     ; x8 *= 5
adrp x9, #0xfffffe0007de5000
add  x9, x9, #0x658
add  x8, x9, x8, lsl #3     ; 步长 40 字节
ldrh w8, [x8, #8]
```

表基址 `0xfffffe0007de5658`，**步长 40，上限 50 项**。

**读表内容**：每项前 8 字节形如 `0x0050000000041462` —— 高 32 位是标志，低 32 位是**递增的字符串偏移**。
用 `KB + 偏移` 解码（`KB = 0xfffffe0007004000`）：

```python
KB + 0x41462 -> "port set"      # 长度 9，下一项 0x4146b 正好 +9 ✓ 链式自洽
```

## 10. 表内容（前 14 项）

| 索引 | 标志 | 类型名 | 尺寸 |
|---|---|---|---|
| 0 | 0x500000 | `port set` | 0x0 |
| 1 | 0x500000 | `port` | 0x2fc |
| 2 | 0x400000 | `service port` | 0x3f8 |
| 3 | 0x400000 | `bootstrap port` | 0x3e0 |
| 4 | 0x400000 | `weak service port` | 0x2fc |
| 5 | 0x400000 | `connection port` | 0x1f4 |
| 6 | 0x200000 | `conn port with ool port array` | 0x260 |
| 7 | 0x500000 | `notification port` | 0x80 |
| 8 | 0x500000 | `exception port` | 0x260 |
| 9 | 0x400000 | `timer port` | 0x260 |
| 10 | 0x500000 | `reply port` | 0x40 |
| 11 | 0x500000 | `special reply port` | 0x40 |
| 12 | 0x200000 | `weak reply port` | 0x27c |
| 13 | 0x0000 | （空名，保留项） | 0x140 |

**⇒ 这是 Mach IPC 的「端口类型」表。对象 +0 的字节是 port kind，取值 < 0x32。**

## 11. 因此：越界写发生在 Mach 端口对象的容器上

结合调用链：

```
port 对象 x22
  [x22]        = port kind（< 50，索引上面那张表）
  [x22+0x10]   = w19
  [x22+0x38] / [x22+0x3a] = 两个 u16，互相比较
  [x22+0x48]   = PAC 认证指针（多样性 0x97f6），与全局 0x7de5650 比较
  [x22+0x68]   = 容器描述符（PAC 认证，多样性 0xb9dc）  ← OOB 函数操作的就是它
```

**OOB 函数语义**：容器在 `port+0x68`，`ldr w8,[x9,#8]` 是元素计数，
`str x9,[x13]` 是「追加到 slot[计数]」。**27.0.1 在容器已满时仍然写这一格。**

## 12. 可达性（这是与之前所有候选的本质区别）

**Mach 端口是用户态最基础的 kernel 对象**：
- `mach_port_allocate()` 任意 app 可调
- `mach_port_insert_right` / `mach_port_deallocate` / `mach_port_mod_refs` 全部无 entitlement
- 上表的 13 种端口类型，`service port` / `connection port` / `reply port` 等
  在 IPC 消息收发中自动创建

**⇒ 不需要任何 entitlement，不需要任何特殊 IOKit 服务。这是本项目至今唯一
「Apple 承认 app 可达 + 定位到具体指令 + 入口在任意进程都能碰的子系统」的组合。**

## 13. 仍未证（必须逐条验，不得跳过）

1. **`w8`（计数）能否被推到「容器已满」** —— 需要知道容器的容量从哪来
2. **越界目标是否可控** —— 越界量固定 +16 字节（一格），落在容器之后
3. **写入内容 `x9 = x3 | x2` 的可控度** —— `x2 = x23`、`x3 = w3`（值 3 或 x26）

**注意**：`str w1,[x10,#8]` 在容器满时 `x10=0`，即**写地址 0x8** ⇒ 必然 panic。
**所以触发这件事的第一现象是内核 panic，不是静默破坏。**
这既是坏消息（易被发现）也是好消息（**可用 panic 作为「是否达到满」的探针**）。

## 15. ⚠ 归属冲突：同一条 CVE 有两个候选（必须记住，不要当成已定论）

`out/NAMED-CHANGED.md:81` 之前把 **CVE-2026-112507** 归给**网络栈**：

```
| CVE-2026-112507 | 越界写 → 写内核内存 | 网络栈（IPv6 输入 / pf） |
```

**但那是「最可能的落点」式的推断**（依据是「13 条 Kernel CVE 高度集中在网络栈」），
不是指令级证据。它指向的候选是 `nat464_translate_64/46`，
形态为 `cmp x28, w25, sxtw; b.hs` + `cmp x28, x8; b.lo`（±上下界）。

**本文件的 Mach IPC 归属是另一条更直接的证据链**：
解出 13 个端口类型名（`port set` / `connection port` / `reply port` …），
链式自洽；且修补点是一次**未受上界约束的 `str`**（写，不是读）。

### 因此存在三种可能

1. **112507 = Mach IPC 这条**，网络栈那条是另一个 CVE（或干脆不是安全问题）
2. **112507 = 网络栈这条**，Mach IPC 这条是未编号的另一处修补
3. 两者都是越界写，Apple 只公开了一个编号

**无法用静态方法判定。** 但有一点是确定的：

| 候选 | app 可直接触达 | 前置条件 |
|---|---|---|
| `nat464_translate_64/46` | **否** —— 需构造 NAT64/CLAT 报文 | 网络位置或蜂窝路径 |
| **Mach IPC 端口容器（本文件）** | **是** —— `mach_port_*` 无 entitlement | 无 |

**所以即便归属错了，Mach 这条在可达性上仍然更有价值，实验优先级不变。**

### 纪律

- 在实验给出结果前，**不得在任何地方写「112507 就是 Mach IPC」**
- 若实验打不出 panic，应当转去查 `nat464_translate_64` 的写入侧
  （那条需要判断 `b.hs`/`b.lo` 之后是否有 `str`）
