# KERNEL-UAF-SIG — 用桩调用差分重做 27.0.1 vs 27.2 内核差分

README
1. 公告 `out/advisory-27.2.json` 里 Kernel 组件 14 条，其中 10 条是 UAF / 竞态 / 内存管理。
2. dChk 只看新增的 `cmp`+条件分支，看不见新增的 `bl`（retain / release / lock）——UAF 修复补的正是 `bl`。
3. 所以换判据：数 4 类已命名的桩目标调用次数，而不是数分支。
4. **桩目标的 VA 会随构建漂移**，四个目标在 27.2 全部换了地址，必须在每个构建里按函数体形状重新认。
5. 差分范围：`com.apple.kernel`（公告点名的 Kernel 组件）。
6. 结果：27.2 里 **3 个函数**的锁类调用比 27.0.1 多，**0 个**函数的 retain/release 调用有变化。
7. 3 条全部手工读过配对与改动点；其中 2 条确认是「新增加锁」，1 条判为内联膨胀、不算。
8. 覆盖只有 27%（363/1324 个有调用的函数能跨构建配对），剩下的未配对，不下结论。
9. 所有「调用 0 次」的旧结论都必须先声明桩解析状态。
10. 自动判据一律标「未手读」；本文件里只有「手读结论」列是结论。

## 1. 判据

四个目标（每个构建里**按函数体形状重新认**，不沿用 VA）：

| 类 | 27.0.1 | 27.2 | 形状判据 |
|---|---|---|---|
| `lock` | `0xfffffe000ab4e274` | `0xfffffe000ab9e274` | `mrs tpidr_el1; ldr w9,[x19,#0x4f8]; add x10,x0,#8; casa` |
| `unlock` | `0xfffffe000abd3f78` | `0xfffffe000ac25344` | `casl w2,wzr,[x8]`，`w2` 为 cpuid |
| `rcinc` | `0xfffffe000b266a30` | `0xfffffe000b2bcb34` | `mov w8,#1; add x9,x0,#0x24; ldadd w8,w9,[x9]` |
| `rcdec` | `0xfffffe000ab5c2a8` | `0xfffffe000abac278` | `mov w8,#-1; ldadd w8,w0,[x0]` 族 |

按形状扫描后，27.0.1 命中 `lock` 437 个 / `unlock` 20 个 / `inc` 3 个 / `dec` 127 个函数；27.2 为 439 / 20 / 3 / 128。**这四个「类」是多函数集合，不是单点**——单点只覆盖 25 个函数（28 次调用），漏得太多。

调用计数：函数体内 `bl`/`b` 目标落在上述集合里就计数（kext 侧还要先过桩表）。

## 2. 我自己踩的两个坑（都影响了结果，必须记）

**坑 1：`md.disasm()` 遇到无法解码的 4 字节会停住。** 一个 716 条的函数只解出 299 条就没动静，导致 27.0.1 侧少算 400 多条指令的调用。改成逐 4 字节解码、解不出就跳过的重同步扫描后，总调用数从 1,603 涨到 2,156（27.0.1）。**之前那一版「3 个候选」是截断产物。**

**坑 2：用「指令序列掩码签名」跨构建配对是错的。** 掩码签名把助记符序列算进哈希，而**补丁本身就是在插指令**——被修补的函数签名必然变，配对必然掉出集合。我第一版跑出「14,348 对、0 差异」，那不是阴性，是**把要找的东西排除了**。
改用**字符串交叉引用集合**配对：插入一条 retain 不改字符串引用，所以配对能活下来。代价是只能配上引用字符串的函数。

## 4. 候选表

| 27.0.1 → 27.2 | 新增 retain | 新增 release | 新增 lock | 新增 unlock | 手读结论 |
|---|---:|---:|---:|---:|---|
| `0xb3bca00` → `0xb4133f4`（`initWithTask`） | 0 | 0 | **+1** | 0 | **真·新增加锁**：27.0.1 内联 `ldr x16,[x17,#0x28]!` + `autda` 直接取字段；27.2 改成先 `bl 0xac70a5c`（PAC 校验：`sub x1,x0,#0x768` + `adds`/`b.hs`）再 `bl 0xac9cbb0`（`add x10,x0,#8; casa` = 真 `lck_mtx_lock`），然后才 `str x0,[x19,#0x18]` |
| `0xb0e5f8c` → `0xb13b830`（`proc_prepareexit_wait`/`waitcoll`） | 0 | 0 | **+1** | 0 | **真·锁定语义改变**：同长度 1115 条，锁位置 {109,691,709,958,1097} → {109,**117**,691,709,958,1097}。差别在 #117：27.0.1 是 `bl 0xb0a29fc`，其头是 `add x8,x0,#0x638; swp xzr,x19,[x8]`（**无锁 swp 抢占**）；27.2 换成 `bl 0xb0f80f0`，其头是 `mrs tpidr_el1; ldr w9,[x19,#0x4f8]; add x21,x0,#0x58; casa x8,x9,[x21]; cmp x8,#0; b.ne 慢路径`（**对象内 0x58 处的 mutex**）。同一处调用从 swp 改成 mutex |
| `0xad386e0` → `0xad0684c`（`m_object_paging_throttle_stats`） | 0 | 0 | **+1** | 0 | **判为内联膨胀，不算**：函数长度 624 → 4468 字节（7.1×），只共享 1 个字符串，旧版独有的字符串在两个新版中都消失——是同名逻辑被内联重写，不是定点补锁 |

三条都**没有**新增 retain/release 调用。

## 5. 这轮没做到的

1. 配对只覆盖 27%（363/1324）；961 个有调用的函数配不上，未查。
2. 判据只统计**一层** `bl`：新增的锁如果没有直接 `bl` 到锁函数（而是进了某个内部加锁的 helper），会被记成「callee 变了」而不是「加了锁」——候选 2 正是这种形态，靠手读才判出来。
3. 只看 `com.apple.kernel`，其余 300 个 kext 未做（公告只说组件，没说 kext）。
4. `IOFree`/`kfree` 仍未识别，所以「裸内存释放」这条线依然没有判据。
5. 新增函数（27.2 比 27.0.1 多 50 个）天然配不上，未逐个看。

## 6. 直答

**有。`com.apple.kernel` 里 27.2 新增了加锁的函数共 3 个，其中 2 个（`initWithTask` 类、`proc_prepareexit_wait` 类）手读确认是真的锁定变更，1 个是内联膨胀；新增 retain/release 的函数 0 个。**

这对应公告里「improved locking / race condition」那一条（CVE-2026-112501，「A race condition was addressed with improved state handling」），对应不上「use-after-free ... improved memory management」那 6 条——那 6 条在 `com.apple.kernel` 里**没有留下 retain/release 的调用次数指纹**，可能落在其它 kext，也可能是通过 `IOFree` 这类我没有判据的路径修的。

## 5. 可达 kext 的锁差分

### 5.1 方法（VA 每构建重认 + 序号对齐 + 长度校验）

kext 侧比 kernel 侧多一层：`bl` 的目标是**桩 VA**，必须先过桩表（27.0.1 `out/stubs.json` 19,938 个；27.2 现建 `/tmp/stubs272.json` 19,934 个，少 4 个）。

跨构建配对我试了三种，前两种都失败，只有第三种站得住：

| 配对法 | 结果 | 为什么 |
|---|---|---|
| 指令序列掩码签名 | 14,348 对、0 差异 | **把补丁本身排除了**：插一条指令签名就变 |
| 字符串交叉引用 | IOSurface 配对 0 | 只有 133/1,330 个函数引用字符串，且互相重叠导致全部并列 |
| **序号对齐 + 长度校验** | **1,328/1,330 长度完全相等** | IOSurface 函数数两版都是 1,330，VA 差恒为 `+0x4e3d0`（尾部 +0x4e3e8） |

序号对齐这次是**被证实的**，不是假设：1,330 个函数按序号逐对比较字节长度，1,328 对完全相等，只有 2 对变了长度。若序号错位，长度不可能这样对齐。

### 5.2 IOSurface 加锁差分结果

| 项 | 27.0.1 | 27.2 |
|---|---:|---:|
| 函数数 | 1,330 | 1,330 |
| 有锁类桩调用的函数 | 227 | 227 |
| `lock` 调用 | 162 | 162 |
| `unlock` 调用 | 179 | 179 |
| 引用计数 +1 / −1 | 70 / 9 | 70 / 9 |
| 函数内新增原子/锁指令（`casa`/`casl`/`swp`/`ldaxr`/`stxr`/`ldadd`…） | — | **0** |

**锁的调用次数和锁指令的位置，两版完全一致。IOSurface 在 27.2 没有新增任何加锁。**

### 5.3 但 IOSurface 确实改了两个函数（`#799`、`#802`）

两版唯一长度变化的两处，且**相邻**。改动不是锁，是**新增状态标志 `obj+0xf1`**：

`#802` `0xa346364` → `0xa394744`（57 → 59 条）：
```
 ldr x0, [x0, #0x150]
 bl  <同一个桩>
+mov w8, #1
+strb w8, [x20, #0xf1]      ← 新增：置标志
 ldr x21, [x19, #0x188]      ← 遍历 +0x188 的链表
```

`#799` `0xa3460f0` → `0xa3944c0`（65 → 69 条）：
```
 bl  <同一个桩>
+ldrb w8, [x21, #0xf1]       ← 新增：读标志
+tbz  w8, #0, <继续>
+add  w20, w20, #0x1b       ← 返回码 0x2bd → 0x2d8
+b    <收尾>
 ldr x8, [x19, #0x188]
```

手读结论：一个函数**置位** `+0xf1`，另一个在遍历 `+0x188` 链表之前**检查**它，命中就走新的返回码 `0x2d8`。这是**状态标志守卫**（防止重复 detach/重复遍历），**不是锁定**。公告对 IOSurface 那条（CVE-2026-112477）写的是 improved locking，但在这个二进制里它没有表现为新锁。

未能证实的部分我留白：这两处是否就是 CVE-2026-112477 的修复，**没有证据**，只能说「27.2 在 IOSurface 里只改了这两个函数，改的是状态标志」。

### 5.5 `IOFree` 判据：没找到

三个方向都试了，全部落空：

| 方向 | 命中 | 手读结果 |
|---|---:|---|
| `[x0,#负偏移]` 取分配头 | 0 | 形态在这个内核里不成立 |
| `sub xN, x0, #imm` 后再 load | 2 | 都不是释放：`0xb43f0d0` 是 `memmove`（`sub x3,x0,x1` 算重叠）；`0xac1f668` 是 PAC/typed-pointer 校验（`sub x1,x0,#0x768; orr #0xf00000000000000; adds …; b.hs`） |
| `cbz x0` + 尾跳（薄包装） | 65 | 逐条看前 8 条，全是 getter / 断言 / 转发，**没有一个是释放** |
| 单 `bl` 转发（≤6 条） | 1 | `0xb43664c`：`bl 0xb43665c` 后接续，不是释放 |

**结论：`IOFree` 判据没有找到。** 换方向：`IOFree` 在 XNU 里最终走 `kheap_free(ptr, size)`，**不加分配头**——这解释了「负偏移」为什么 0 命中。下一步应该反过来先认 **`IOMalloc`/`kheap_alloc`**（分配侧有返回值、有 size 入参，比释放侧好认），再用「谁调用了它的反向操作」定位 `IOFree`。

### 5.6 直答

**问 1：IOSurface 在 27.2 新增了哪些加锁？**
**没有。** 1,330 个函数逐对比较（1,328 对长度相等，序号对齐已被长度证实）：锁类桩调用 162/179/70/9 两版完全相同，函数体内新增原子/锁指令 **0** 条，符号表为空、chained fixups `imports_count = 0`，所以也不存在「换成新符号」的可能。
27.2 在 IOSurface 里只改了两个相邻函数（`#799`/`#802`），改的是**新增状态标志 `obj+0xf1` 的置位与检查**和一条新返回码 `0x2d8`，不是锁。它是否是 CVE-2026-112477 的修复，**没有证据**。

**问 2：`IOFree` 的判据找到了没有？**
**没有。** 四条路径全落空，详见 §5.5。6 条 UAF 里走裸内存释放的那部分，目前仍然**没有判据**，所以扫不了。
