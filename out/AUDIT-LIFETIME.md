# 生命周期缺陷审计（三种静态形态）

1. 靶子：普查里被明确排除的那一类——`out/CENSUS-DISPATCH-TABLES.md` §6 自陈「只覆盖长度/索引，不碰状态机、竞态、引用计数」。
2. 范围：2266 个 selector 的全部 handler，按 `LC_FUNCTION_STARTS` 展开 **5 层尾调用**，共 **2371 个函数**。
3. 三种形态：**悬垂存储**（形态 1）/ **release 后使用**（形态 2）/ **解锁后使用**（形态 3）。
4. 关键基础设施（本轮新做）：kext 的**符号桩表**——`adrp x17,slot / add / ldr x16,[x17] / braa x16,x17` 共 19,938 个，全部解出真实目标（`out/stubs.json`），这才让「这个 `bl` 到底调的是谁」变成可判的。
5. 关键判据（现场读出，非推断）：`mov x17,R / autda x16,x17 / ldr x8,[x16,#0x28]! / blraa x8,x16` 里的 **`#0x28` 就是 `OSObject::release` 的虚表槽**，`R` 是被释放的对象。
6. 假阳性纪律：自动结果一律先标候选；**每一条都手读了反汇编**。本轮自动检测器又踩了 3 类假阳性（详见 §2.2），全部修掉后候选从 7 掉到 2。
7. 结果：形态 1 手读 2 条 → **都是良性**；形态 2 自动覆盖 191 个释放点，**release 后使用 0 条**（检测器在正控制上验证通过）；形态 3 **锚点没建立起来，覆盖 0，不给结论**。
8. 直答：**2266 个 selector 里，没有静态可判的悬垂存储、没有 release 后使用，解锁后使用没有可判覆盖。**
9. 手读总数 **4 条**（2 条形态 1 候选 + 1 条正控制 + 1 条 ivar 替换范式）；自动覆盖 2371 个函数 = 2266 个 handler + 105 个尾调用目标。
10. 本轮真正的收获不在「找没找到」，而在 §5：桩表让 kext 的外部调用第一次可判；以及 `ivar` 维护的三种**正确**写法被逐个读到，可以当后续审计的对照基线。

## 1. 方法

### 1.1 扫描范围

- 起点：`out/census.json` 的 2266 个 handler VA。
- 展开：每个 handler 顺着 `b <imm>` 尾调用走，最多 5 层，只跟本 kext 内的函数起点 → 2371 个函数，去重后 146 个函数里出现了释放点。
- 每个函数最多看 500 条指令；**遇到 `ret`/`retab`/无条件 `b` 就停**（线性扫描跨基本块不可达，这是本轮最大的精度来源，见 §2.2）。

### 1.2 释放点判定

虚释放（已验证）：

```
0xa10533c: ldr  x16, [x23]          ; x16 = 原始 vtable
0xa105340: mov  x17, x23            ; x17 = 对象身份
0xa105344: movk x17, #0xcda1, lsl #48
0xa105348: autda x16, x17           ; x16 = 认证后的 vtable
0xa10534c: ldr  x8, [x16, #0x28]!   ; #0x28 = OSObject::release 槽
0xa105350: mov  x0, x23
0xa105358: blraa x8, x16
```

这个判据在 `com.apple.iokit.IOHIDFamily 0xfffffe000a1052cc` 上被**正控制验证**：该函数报出两个释放点，正好是我手读看到的两个（0xa105358 释放临时对象 `x23`、0xa10538c 释放旧 ivar `[x19+0x120]`）。

### 1.3 形态 2 的使用判定

同一基本块内，释放之后对该对象寄存器的任何 `ldr/ldrb/str/stp/ldaxr/...`（`mem.base == 被释放的寄存器`）→ 报 S2-use。寄存器被 `mov`/`ldr`/`autda` 重新赋值即视为身份失效。

## 2. 形态 1：悬垂存储

### 2.1 机械结果

判据：`str xN, [xSelf, #off]`，`xN` 是**调用返回的新指针**，且该偏移**没有先释放旧值**。

| 阶段 | 候选数 |
|---|---:|
| 第一版（未做基本块/寄存器失效处理） | 45 |
| 修掉「self 寄存器被 `adrp x0` 覆写」 | 7 |
| 再加「`str xzr,[self,#off]` 视为该偏移已重置」 | **2** |

剩下 2 条：

| kext | handler | 存储点 | 结论 |
|---|---|---|---|
| `com.apple.driver.AppleARMPlatform` | `0xfffffe00086782e8` | `0x8678358: str x0,[x20,#0x110]` | **良性**：`0x110` 在本函数内是首次赋值（`init`/`start` 路径），且同函数内 `0xe8`/`0xf0` 走的是「先 `str xzr` 清零 → `bl IOFree` → 再 `IOMalloc` → 存回」的正确替换序列 |
| `com.apple.driver.AppleSEPManager` | `0xfffffe000961f338` | `0x961f43c: str x0,[x20,#0xe0]` | **良性**：前面有 `ldr x8,[x20,#0xe0]; cbnz x8, 跳走`，**只在该 ivar 仍为 NULL 时赋值**，不存在覆盖 |

### 2.2 这一节踩掉的 3 类假阳性（都要记下来）

1. **`self` 寄存器被覆写**：`adrp x0, <字符串>; add x0, x0, #imm; bl <alloc>` 之后 `x0` 已经是新对象，但我的 `selfr` 还认为 `x0` 是 handler 的 target。→ 8 条假阳性（`IOUSBHostFamily` 的 `str x25,[x0,#0x40]` 全是这一类：`x0` 是刚分配的结构体，不是 self）。
2. **基本块边界**：线性扫过 `retab`/`ret`/`b` 之后的内容属于**另一个基本块**，不可达。`IOGPUFamily 0xfffffe000a02299c` 的「释放后又用 x20」就是这么来的——`0xa022b98` 释放完就 `retab` 返回了，`0xa022bec` 那段是冷路径（还带 `bl 0xa05f550` 的断言打印）。→ 5 条假阳性。
3. **`autda` 覆盖目标寄存器**：`autda x16, x17` 之后 `x16` 是 vtable 而不是对象，上一轮的 `rel[x16]` 已经失效。`IOHIDFamily 0xa105bf4` 的「释放后访问 `[x16,#0x28]`」就是这一类——那其实是**第二个对象**的释放序列。→ 若干。

### 2.3 结论

**形态 1 无真实候选。** 机械 2 条，手读 2 条，2 条都是良性，且良性理由各不相同（首次赋值 / NULL 保护）。

### 3.2 正控制

检测器不是「永远返回空」：在 `IOHIDFamily 0xfffffe000a1052cc` 上它报出的两个释放点与我手读的完全一致。所以「0」是有意义的 0，不是哑火。

### 3.3 覆盖的真实限制（必须写清）

判据只在**同一基本块**内成立。跨基本块的「释放 → 分支 → 使用」不跟踪。所以本节的准确表述是：**在 146 个含释放点的函数里，释放点之后的线性后继里没有出现对该对象的访问。** 分支合流处的使用不在覆盖范围内。

### 3.4 顺带读到的正确范式

`IOHIDFile` 那段（`0xfffffe000a1052cc`）是标准的「替换 ivar」写法：

```
0xa10536c: ldr x0,[x19,#0x120]      ; 取旧值
0xa105370: cbz x0, 跳过
0xa105374..0xa10538c: 虚释放 #0x28   ; 释放旧值
0xa105390: str x22,[x19,#0x120]     ; 存新值
```

旧值先释放、再把新值存进同一偏移——**顺序是对的**。14 个 ivar 释放点里，没有一个出现「存新值但没先释放旧值」（否则会被形态 1 抓到）。

## 5. 旁产：本轮真正开阔了视野的两件事

### 5.1 kext 的符号桩表（可复用资产）

`out/stubs.json`：280 个 kext 共有 **19,938 个桩**，全部解出目标 VA。桩形如：

```
adrp x17, <__DATA_CONST slot>
add  x17, x17, #imm
ldr  x16, [x17]
braa x16, x17            ; PAC 认证的间接跳转
```

意义：**以前 kext 里 `bl 0x88edd68` 会被当成「调用了一个不存在的函数」**（那地址不在 `LC_FUNCTION_STARTS` 里，因为桩区不被登记为函数）。现在可以还原成「调用了 kernel 的某个导出函数」，并且能按「多少个 kext 共用同一个目标」给 API 热度排序：

| 目标 | 共用 kext 数 |
|---|---:|
| `0xfffffe000b268c20` | 270 |
| `0xfffffe000b268bbc` | 270 |
| `0xfffffe000b265500` | 270 |
| `0xfffffe000b2660a0` | 270 |
| `0xfffffe000b266a30` | 268（`ldadd` 自增 `[x0+0x24]`，引用计数自增形态） |

### 5.2 三种「正确」的 ivar 维护写法（可当后续审计的对照）

1. **替换**：`ldr 旧值 → cbz → 虚释放 #0x28 → str 新值`（IOHIDFile）。
2. **清空再释放**：`str xzr,[self,#off] → bl IOFree → str 新值`（AppleARMPlatform `0xe8`/`0xf0`）。先把 ivar 置 NULL 再 free，这样即使中途被打断也不会留下悬垂指针。
3. **NULL 保护的单次赋值**：`ldr 旧值 → cbnz 跳过 → bl 分配 → str`（AppleSEPManager `0xe0`）。

这三种都不是 bug，但**它们是判断「第 4 种写法是不是 bug」的基线**——下一轮碰到「存了但没释放旧的」「释放了但没清空」「没 NULL 保护就覆盖」时，才有对照。

## 4. 用桩表重做形态 2/3（跨基本块）

### 4.1 上一轮形态 3「锚点不存在」是假的，根因是桩

上一轮我写「2371 个函数里没有任何可机械认定的加解锁点」。**那是假阴性，根因是桩间接跳转**：

kext 调内核函数走的是桩，所以 `bl` 的**原始目标是桩 VA**，不是真实函数地址。我上一轮拿原始 `bl` 目标去比 `UNLOCK` 集合，当然一次都匹配不上。

用桩表把 `bl` 目标解析成真实 VA 之后，同一批 2371 个函数里：

| 项 | 桩解析前 | 桩解析后 |
|---|---:|---:|
| `bl` 调用点 | 6,393 | 32,245 |
| `lck_mtx` 加锁调用 | 0 | **304** |
| `lck_mtx` 解锁调用 | 0 | **436** |
| 引用计数自增调用 | 0 | 9 |

**「调用 0 次」是工具缺陷，不是目标性质。** 这条要记住：以后任何「某函数没被调用」的结论，都必须先声明桩是否已解析。

### 4.2 桩目标命名（`out/stubs-named.json`）

19,938 个桩 → **4,153 个不同目标**，其中 4,150 个能取到函数体（3 个取不到）。前 200 个里 **15 个手读命名**，其余 185 个只给了特征标签（`ldadd`/`cas`/`sev`/`brk`/负偏移…）和函数头 8 条指令，**未命名**。

手读命名出的关键 6 个：

| 目标 | kext 数 | 语义 | 证据 |
|---|---:|---|---|
| `0xfffffe000b266a30` | 268 | 引用计数自增 `@[obj+0x24]` | `mov w8,#1; add x9,x0,#0x24; ldadd w8,w9,[x9]` |
| `0xfffffe000b264d84` | 23 | 引用计数 −1 `@[obj+0]` | `mov w8,#-1; ldadd w8,w0,[x0]; ret` |
| `0xfffffe000abd3390` | 119 | **`lck_mtx` 加锁快路径** | `casa 0→cpuid` on `[x0+8]`，cpuid 取自 `tpidr_el1+0x4f8`，失败跳慢路径 |
| `0xfffffe000abd3f78` | 120 | **`lck_mtx` 解锁快路径** | `casl cpuid→0` on `[x0+8]`，不匹配跳慢路径 |
| `0xfffffe000b43f0d0` | 152 | `memmove` | `sub x3,x0,x1; cmp x3,x2; b.lo`（重叠检测） |
| `0xfffffe000b43f280` | 149 | `memset`/`bzero` | `eor x1,x1,x1` 后 `stp x1,x1,[x0]` 批量填 0 |

**顺带解掉了 `OSObject` 虚表的两个槽位**（在 IOGPU 的「retain 新的 / release 旧的 / 赋值」惯用法里同时出现）：

| 槽 | 语义 | 现场 |
|---|---|---|
| `+0x20` | **`retain`** | `IOGPU 0xa0411b8: ldr x8,[x16,#0x20]!; blraa` 作用在**新**对象，随后 `+0x28` 作用在**旧**对象，然后 `mov x19,x20` |
| `+0x28` | **`release`** | 同上，第 4 轮已独立验证 |

这条把上一轮 §3 里「取指针 → 解锁 → 使用」的性质直接定了：**锁内 `+0x20` 就是 retain，解锁后用是对的**。

### 4.3 方法：CFG + 别名 id + 前向数据流

- 基本块按「分支目标 + 分支后继」切分；后继 = 条件分支的 **target + fallthrough**、无条件 `b` 的 target、`ret/retab` 无后继。
- 寄存器身份用**别名 id** 而不是寄存器名：`mov x19,x0` 之后，释放 `x0` 等于释放 `x19`。
- 调用破坏 caller-saved（`x0..x18`）的别名，callee-saved（`x19..x28`）的身份跨调用保留。
- 状态 `(freed{id→地址}, stale{id→解锁地址}, canon{reg→id}, objlike{id})` 沿 CFG 前向传播，4 轮定点。

**这一步我自己又踩了 3 个工具缺陷（都要记）**：

1. **`succ_of` 漏了条件分支的 fallthrough** → 所有 `cbz`/`b.eq` 都成了死路，数据流根本跨不出第一个条件分支。前三次跑全是 0 候选，就是这个原因。
2. **`cbz x19` 被当成「写 x19」** → 身份在比较指令处被清掉，后继块认不出 x19。把 `COND` 一族排除出「写」判定才修好。
3. **「取 vtable 的 `ldr xD,[R]`」被当成一次使用** → 「解锁后 release 对象」这种**正确**写法全被报成 UAF。修法：`ldr xD,[R]` 之后 4 条内出现 `autda xD, …` 就判为 vtable 取指，不算使用。

修完这 3 条，候选从 0 → 81（含重复）→ 去重 24。
