# 27.2 RC 候选漏洞点（函数级人工确认）
- 生成：2026-10-23
- 上游：`PATCH-MAP-27.2.md`（kext 级）、`out/kfunc-*.json`（函数级）

## 0. 先说方法论上的两个否定结果

1. **release notes 没有安全内容**。`ios-ipados-27_2-release-notes` 只有 SDK/API 变更（AppTrackingTransparency、Health、Nearby Interaction 等），零 CVE 条目。安全清单要等 27.2 正式版发布后上 support.apple.com。因此当前唯一信息源是二进制。
2. **按"新增比较/分支"排序会产生假阳性**。内核头号候选 `0x3eef8f0 → 0x3f435e4` 的反汇编前 45 条，差异全部是 `adrp/add/ldr` 的数据偏移（`#0x88a000` → `#0x88e000`），属于链接布局漂移，不是逻辑修补。`dChk` 的差异来自函数后半段对齐，不是新增检查。

**结论：数量级信号（kext 级 1.2%）可信，单函数排序只作线索，必须人工看反汇编。**

## 1. IOUSBHostFamily（61 变动 / 1,976 函数）

**候选：`0x2b2e81c` → `0x2b6ee9c`（164 → 196 字节，+32，dChk +6）**

这是一个真实的校验重写，不是布局漂移。关键差异：

| 27.0.1 | 27.2 |
|---|---|
| `ldrb w8, [x1, #3]` 直接读 | 先 `mov w8, #0`，再 `ldrb w10, [x1, #3]`，`and w9, w10, #3` |
| 无 `x2` 判空 | **新增 `cbz x2, #0x98`** |
| 无 `x3` 判空 | **新增 `cbz x3, #0x98`** |
| `cmp w0,#2 / #3 / #8` 直跳 | 改为 `cmp w0,#2` + `b.gt` + `b.lo` 的两段式区间判断 |
| `cmp w9,#1; b.ne` | 改为 `cmp w9,#1` + `ccmp w8,#0,#4,eq` 联合条件 |

判读：输入来自 USB 描述符解析路径（`bInterval`/`wMaxPacketSize` 一类字段：`ldrh w9,[x1,#4]; and w9,#0x7ff` 是 11 位长度字段）。27.2 增加的是**空指针守卫 + 位域掩码 + 区间校验**。空指针本身不可利用，但同一函数内的位域掩码收紧，往往对应"字段未校验导致越界/除零"类问题（原版有 `udiv w11, w10, w9`，除数来自 `w9 = 描述符字段 & 0x7ff`，**原版没有对 `w9 == 0` 的检查路径**，B 版用 `ccmp` 补上了）。

**这是本轮最有价值的发现**：27.0.1 侧存在一个"除数为 0"的路径，27.2 补了。

## 2. com.apple.security.sandbox（23 变动 / 658 函数）

**候选：`0x2d8eedc` → `0x2dcf568`（120 → 152 字节，dChk +3）**

B 版新增序列：

```
ldr x9, [x0, #0xf8]
and x10, x8, #0x12
cmp x10, #0
ccmp x9, #0, #0, eq
b.ne #0x50
ldr x0, [x19, #0xf0]
bl  <thunk>          ; 经 GOT 的导入函数
cmp w0, #7
b.ne #0x78
```

判读：新增一次"标志位掩码 + 状态联合判断"，随后**调用一个外部函数并把返回值与 7 比较**。`bl` 目标是 `braa` 跳板（导入符号），无符号表无法命名，但形态是"策略/授权查询返回枚举，只有等于 7 才放行"。

在沙箱 kext 里出现新的授权判定分支，属于链上最值得追的一类改动（沙箱策略绕过）。

## 5. 守卫扫描（全量 301 kext）

口径：B 中 `cbz/cbnz xN`（或 `cmp xN,#0; b.eq`）紧邻 `ldr [xN]`，且 A 同位置无守卫。
结果：**81 个函数新增守卫**。分布 top：`com.apple.kernel` 27、`ASIOKit` 10、`AppleSARService` 5、`AppleMultitouchDriver` 5、`EXBrightKext` 4、`AGXG18P` 4。

### 已人工确认：AppleH16ANEInterface `0x1837fe8 → 0x1894764`（688→756B，守卫 0→7）

27.0.1：
```
ldr x0, [x19, #0x330]
bl  #0x42d40          ; x0 可能为 NULL，无判空
ldr x1, [x19, #0x338]
ldr x0, [x1, #0x40]   ; 直接解引用 x1，无判空
```
27.2：
```
ldr x0, [x19, #0x310]
cbz x0, #0x3c         ; 新增
bl  #0x38b84
ldr x1, [x19, #0x318]
cbz x1, #0x58         ; 新增，在解引用之前
ldr x0, [x1, #0x40]
```
同一函数内连续 7 处新增判空，且结构体字段偏移从 `#0x330/#0x338/#0x388` 变为 `#0x310/#0x318/#0x368`——**结构体本身也改了**。这是驱动 teardown 路径的空指针守卫加固，形态属于"修 NULL deref / 生命周期错"。

### 对第 3 节结论的更正
`com.apple.kernel 0x3eef8f0` 之前判为纯布局漂移，守卫扫描显示守卫数 2→6、体积 +80B，**确实新增了检查**，原判过严。布局差异与逻辑修改可以同时存在。

### 方法学收益
守卫检测比"比较指令增量"稳定：它锚定在"解引用前的判空"这一语义模式上，不受 `adrp/movz` 布局漂移影响。81 条命中里可以人工确认的密度明显高于 358 条 `dChk` 排序。

## 6. sandbox 那条"授权分支"的追查结果（降级）

调用链解析：
```
27.2 FUN_fffffe000a93bc38 (sandbox)
  └─ BL → thunk 0xfffffe000a95432c
       └─ GOT slot 0xfffffe000843ad78 = 0x8011000003e37ebc
            └─ com.apple.kernel +0x3e2febc
                 └─ 实现：return *(u16 *)(param_1 + 0x72);
```

即：**新调用只是一个 16 位字段的 getter**，sandbox 拿它和 7 比较：

```c
if ((uVar4 & 0x12) == 0 && *(long *)(param_1 + 0xf8) == 0) {
  iVar2 = get_field16(*(long *)(param_1 + 0xf0), 0x72);
  if (iVar2 != 7) {           // 不是 7 → 走老路径
     ...
  } else {                     // 是 7 → 置 0x100000000000000
     uVar4 = *puVar1;
  }
```

**结论：这不是新增的安全校验，而是按对象类型（field+0x72 == 7）分流的行为变化**，更像 27.2 引入的新 profile/对象类型。之前把它当成"授权判定加固"是过度解读，**降级为功能变更**。

对比之下，ANE 那条仍然是硬证据：明确新增了 `count < 0x101` 与逐项 `numInputs/numOutputs ≤ 0xff`，并把"越界即 panic"改成"返回错误 0xe00002d1"。

## 7. USB 那条的 27.2 对照（确认，但低危）

27.0.1（`FUN_fffffe000a600dcc`）：
```c
if (param_1 == 2) {
  if ((*(byte *)(param_2 + 3) & 1) != 0) {
    uVar8 = *(ushort *)(param_2 + 4) >> 0xb & 3;
    ...
  }
}
```
直接解引用 `param_3` / `param_4`，并用 `*(ushort*)(param_2+4) & 0x7ff` 作为除数。

27.2（`FUN_fffffe000a64e93c`）：
```c
if ((int)param_1 < 3) {
  if (param_1 < 2) goto ...;
  if (param_1 == 2) { ... }
  if (param_3 != 0) {                       // 新增判空
    uVar4 = *(ushort *)(param_2 + 4);
    uVar2 = uVar4 & 0x7ff;
    if (((bVar1 == 1 && (uVar4 & 0x7ff) != 0) && (param_4 != 0)) && ...   // 新增零值检查
```

**结论**：确认为"空指针 + 除零"加固，与反汇编观察一致。但影响面有限：
- 触发需要 USB 描述符输入（主机/外设模式），**第三方 app 在 iPhone 上拿不到这个入口**；
- 后果是 panic/DoS，不是内存破坏。

**定级：中低。** 可作为链的干扰项，不作为入口候选。

## 10. AppleAVE2：码流解析器新增边界（字符串差分定位）

### 定位方法
字符串集合差分 → 215 条新增诊断串 → 按 kext 聚类 → `AppleAVE2` 62 条，
全是 HEVC/AVC/AV1 码流字段的 "out of range" 校验。AVE 经 VideoToolbox 对 app 可达。

### 改动函数（27.0.1 → 27.2）
`kfunc` 配对 20 个，另有 11 个无法配对；形状分析显示 **34 个函数指令序列完全变化**。

### 已对照的两处改动

**A. 参考帧选择（`0x1488a9c` → `0x14ba30c`）**
```c
// 27.0.1
if (-1 < (int)uVar5) { ... local_90[iVar12] = lVar15; uVar13 = iVar12 + 1; uVar10++; }
} while ((int)uVar10 < (int)param_4);
// 27.2
if ((((int)uVar10 < 4) && ((int)uVar16 < 4)) && (-1 < (int)uVar5)) { ... }
```
`local_90` 是 `long[4]` 栈数组，27.2 显式约束两个计数器 < 4。

**保留意见**：两版都有 `if (3 < param_4) param_4 = 4;`，且外层循环上界就是 `param_4`，
所以 27.0.1 的迭代次数本就被限制在 4。新增的 `< 4` 更像是**防御性冗余**，
不能仅凭这处就断言存在栈溢出。

**B. 帧列表处理（`0x158f784` → `0x15c4928`）**
```c
// 27.0.1
} while (lVar7 < *(int *)(param_1 + 0x20));
// 27.2
iVar3 = *(int *)(param_1 + 0x20);
if (1 < iVar3) iVar3 = 2;
} while (lVar7 < iVar3);
```
循环上界被钳到 2，属**行为限制**（可能是限制处理层数），非越界修补。

### 结论
AVE2 确实是 27.2 改动最集中的解析面，但目前已看的两处都不是"缺检查 → 内存破坏"的形态。
剩余 32 个形状变化函数尚未逐一看。

### 12. 常量集合差分的局限（重要）

尝试用"每对函数的比较常量集合差集"自动找新边界，结果不可用：
```
15bacbc -> 15f017c  new_consts=[0x13b, 0x147, 0x199, 0x33b]
```
这些是 **AVE 日志里的源码行号**（格式串 `%s:%d %s` 的参数），不是边界常量。
同理 `0x1b48`、`0x2e34` 是结构体偏移。

**结论：常量差分被日志行号污染，无法自动识别新增边界。**

### 13. AVE2 总结
- 27.2 对 AVE2 是大规模改造（34 函数形状全变、62 条新诊断串）
- 已看的 3 个热点函数里，真正的边界检查（0x3f/0x40）在 27.0.1 就存在
- 新增的是日志与两处防御性约束，未发现"原本缺检查"的证据
- 剩余 30 个形状变化函数未判读；受日志行号噪声影响，自动化难度高

## 11. AppleAVE2：27.0.1 缺少 7 项参数边界校验（强候选）

### 对照（同一函数，27.0.1 `FUN_...878ddcc` vs 27.2 `FUN_...87c79c8`）

**27.0.1**
```c
if (*(int *)(param_2 + 100) - 1U < 2) {
  if (*(int *)(param_2 + 0x68) - 1U < 2) {
      /* 直接进入，随后把 field_0x1888 等参数交给下游 */
      uVar4 = FUN_fffffe00088cedac(*(undefined4 *)(param_2 + 0x1888));
```

**27.2**
```c
if (*(int *)(param_4 + 0x68) - 1U < 2) {
  if (*(uint *)(param_4 + 0x510) < 8) {
    if (*(uint *)(param_4 + 0x768) < 8) {
      if ((((*(uint *)(param_4 + 0x1888) < 7) && (*(uint *)(param_4 + 0x27f8) < 0x10)) &&
          (*(uint *)(param_4 + 0x2c10) < 0x11)) &&
         ((*(byte *)(param_4 + 0x42c7) < 2 && (*(uint *)(param_4 + 0x27f4) < 0x3f)))) {
        if (*(byte *)(param_4 + 0x32c0) < 0x41) {
```

### 新增的 7 个边界
| 字段偏移 | 上界 | 推测含义（HEVC/AVC 语义） |
|---|---|---|
| `+0x510` | `< 8` | 某维度/层数 |
| `+0x768` | `< 8` | 同上（另一 plane/分量） |
| `+0x1888` | `< 7` | log2 相关（随后传给 `FUN_...8cedac`） |
| `+0x27f8` | `< 0x10` | 参考帧数类 |
| `+0x2c10` | `< 0x11` | 同上 |
| `+0x42c7` | `< 2` | 布尔/枚举 |
| `+0x27f4` | `< 0x3f` | 索引上界 |
| `+0x32c0` | `< 0x41` | 计数上界 |

### 为什么重要
1. **27.0.1 完全没有这些检查**，越界参数会直接流入后续逻辑
2. AVE 经 **VideoToolbox** 对 app 可达（解码/编码自定义码流），**不需要任何私有授权**
3. 与新增的 62 条 "out of range" 日志一一对应——苹果在为这些字段补日志+校验

### 待办
1. 确认这些字段能否由 app 通过 `VTCompressionSession` / `VTDecompressionSession` 属性或码流 SPS/PPS 设置
2. 在设备上构造越界参数，观察是否被接受（27.0.1 应接受，27.2 会拒）
3. 若被接受，追下游使用点，判断是否可造成越界读写

### 重要限定：其中一项有下游校验

`+0x1888` 在 27.0.1 里被传给 `FUN_fffffe00088cedac`：
```c
if (3 < param_1) return 0xfffffc16;   /* 已拒绝 */
return 0;
```
即 **27.0.1 对该字段本来就有 `<= 3` 的检查**（27.2 的新检查 `< 7` 反而更宽松）。
所以这一项不构成"缺失校验"。

其余 6 项（0x510、0x768、0x27f8、0x2c10、0x27f4、0x32c0、0x42c7）的下游消费者尚未追查，
**目前不能断言可造成越界**。

### 追查结果：这 7 个偏移在 27.0.1 里几乎不存在

全 kext 扫描 27.0.1 的 `ldr/ldur` 位移：
```
0x510  被 6 个函数读取
0x768 / 0x27f8 / 0x2c10 / 0x42c7 / 0x27f4 / 0x32c0   —— 0 处
```

说明：**27.2 检查的这批偏移在 27.0.1 的结构体里不存在或位置不同**。
两版之间结构体布局发生了变化，跨版本按偏移比对不可靠。

因此"27.0.1 缺少这 7 项校验"的推断**不能成立**——更可能是 27.2 给**新增字段**加了校验
（配合新功能），而不是修补旧字段的缺失检查。

### 方法论结论
跨版本按结构体偏移对比会失效。可靠的做法只有两条：
1. 在**同一版本内**判断"该字段的使用点是否有边界"（需先精确定位字段语义）
2. 用真机做**行为对比**（同一 API 调用在 27.0.1 被接受、在 27.2 被拒绝）
