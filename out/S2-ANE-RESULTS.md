# S2 收敛：ANE 42 个 dChk>0 函数的校验性质

**日期**：2026-11-01 01:55
**判据**：dChk（条件分支增量）—— 本工程的方法学铁律

## 一、总体

```
改动函数对 155 | dChk>0: 42 | =0: 75 | <0: 38 | 净 dChk: -106
```

## 二、逐个人工判读的三个代表

### 2.1 `0x8c799fc` → `0x8cde270`（dChk=+15）：**数值钳制，非越界修复**
```asm
umull x11, w9, w28
udiv  x11, x11, x10
cmp   x11, #0x64
csel  x11, x11, x28, lo     ; 超 100 取 100
sub   x12, x28, x11         ; 100 - 比值
...
str   w21, [x23, x19, lsl #2]
```
钳的是**百分比数值**；数组下标 `x19` 是循环变量，未变。
→ **算术正确性修复**（利用率不应超过 100%），不是边界检查。

### 2.2 `0x8c11994` → `0x8cc2768`（dChk=+15）：**真索引校验，但索引来自全局**
```asm
ldr  w8, [x19, #0x108]
sub  w9, w8, #0x101
cmn  w9, #0x101
b.hi fail                   ; 字段须在 [0x101,0x201]
ldr  w9, [x9]               ; ← 全局变量 0xfffffe000b91f000+0x7f8
cmp  w9, #3
b.hi fail                   ; 上界 3
add  x10, x10, #0xdd8
lsl  x9, x9, #3             ; ×8
ldr  x9, [x11]              ; 表[全局值]
```
索引源是**内核全局**，不是用户输入。
→ **防御性加固**（全局被破坏时不越界），不是修用户可触发路径。
同类实例：`0x8cc2bf0`。

### 2.3 `0x8d27af8` → `0x8d1ed20`（dChk=+34，最大）：**空指针加固**
新增条件以 `cbz xN` 为主：
```
cbz x20 / cbz x28 / cbz x21 / ldr..⇒ cbz x22 ...
```
→ **NULL 解引用加固**，非边界检查。

## 三、结论

ANE 的 42 个 dChk>0 **绝大多数是防御性加固**（NULL 检查、全局/字段区间校验、
数值钳制），针对的是**内部状态已被破坏**的场景，不是用户可直接触发的越界。

结合子代理的实测（CoreML 300 输入模型 85.7ms → 被 fallback 到 CPU，
ANE 的 IO 计数路径被编译器在用户态挡住）：

> **ANE 的 2 条 OOB write（CVE-2026-112696 / 84494）在当前手段下不可达。**

`H1xANELoadBalancer` 虽可被普通 app 打开，但其 external method 表是**控制面**
（负载均衡/电源），不是 IO 计数路径，打不到上面这些校验点。
→ **决定：暂不把 H1xANELoadBalancer 纳入候选池**，但保留其 method 表作为后续观察点。
