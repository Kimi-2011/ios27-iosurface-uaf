# 27.2 新函数清单（`com.apple.kernel`）

父的前提：`com.apple.kernel` 函数数 21731 → 21781，**+50**。这 50 个是「从无到有」的代码。

**结论：这个前提成立，但要用对方法才能把那 50 个挑出来。我试了三种方法，前两种都给不出，第三种给出 54 个纯插入。**

---

## 1. 三种方法的对比（前两个失败，值得记）

| 方法 | 结果 | 为什么错 |
|---|---|---|
| **地址集合差** `set(f2) - set(f1)` | 21590 个 | 整镜像平移，地址全变，全被当"新" |
| **内容哈希差**（归一化 body 的 sha1） | 3982 个 | body 改一条指令哈希就变 ⇒ 3809 个**改过的**函数全被算成"新" |
| **序列对齐 + 粗键** | **54 个纯插入** / 9 纯删除 / 285 替换块 | ✅ 与 `+50` 的次数差一致 |

### 粗键的定义（关键）

```
键 = (体积 // 32, 前 6 条指令的助记符序列)
```

**用精确 body 哈希当序列元素，等于要求「函数一个字节都没变」才认得出是同一个函数** ——
这就是方法二虚高 20 倍的根因。粗键允许 body 内部变化，只有真正「凭空多出来」的才会成为插入段。

**这条进 `TOOLING-PITFALLS`：序列对齐的元素键必须容忍内容变化，不能用精确哈希。**

## 2. 54 个新函数里，形态上有价值的三个

### `0xabbef50`（204 B）—— **谓词/查询形态，返回 −1 表示失败**

```asm
bti c
cbz   x0, fail
ldrb  w8, [x0, #1]          ; ★ 读 +1 的字节
and   w8, w8, #7            ; ★ 取低 3 位
sub   w8, w8, #1
cmp   w8, #1
b.hi  fail                  ; ★ 要求 (byte&7) ∈ {1,2}
...                          ; 沿 autda 保护指针链走 +0x48 → +0x50 → +0x318
ldr   w0, [x8, #0x18]       ; 取一个 u32
fail:
mov   w0, #-1               ; 失败返回 -1
...
str   x16, [x1]             ; 出参写回
```

**「检查类型字节 → 沿指针链取角色/ID → 取不到返回 −1」**，典型的 `*_for_type` 查询函数。

**假设（未验证）**：与 `__LINKINFO` 新增的 `_task_coalition_role_for_type` 或 `_proc_coalitionids` 对得上。
**但 `__LINKINFO` 只有名字没有地址，我无法把名字绑到这个地址上 —— 这只是形态巧合，不作结论。**

### `0xabe6074`（84 B）—— **带 PAC 保护指针的数组写入（内存安全加固）**

```asm
ldr   x8, [x0, #0x20]       ; 基址
lsl   x9, x1, #3            ; 索引 ×8
csel  x10, x10, x16, eq     ; ★ 越界时选中的是「毒指针」0x2bad_xxxx...
str   w8, [x10]             ; 越界就写到毒地址（立即崩，而不是静默越界）
```

**这是 KASAN / MTE 风格的越界防护存储**，两次（`+0x1c` 和 `+0x48`）。
不是策略检查，是**编译器插入的内存安全helper**。

### `0xac31b24`（152 B）—— **原子位清除 + 位测试**

```asm
bti c
add   ..., ldclr ..., bics ..., b.ne ..., ldrh
```

`ldclr`（原子清除位）+ `bics`（按位测试并设标志）。同属运行时原子操作 helper。

## 3. 54 个里没有「读字段 + 比较 + 跳错误返回」这个最高形态

我按父的判据过了一遍开头指令。分布大致是：

```
裸返回/转发（bti ... b/ret，20–28 B）      若干
编译器断言（udf/brk）                       少数
带 PAC 的越界防护存储                       2 个（0xabe6074 等）
原子位操作（ldclr/bics）                    1 个（0xac31b24）
普通业务函数（pacibsp 开头，中大体积）        多数
谓词/查询（0xabbef50）                      1 个
```

**没有一个呈 `movz/movk #e000` + `cmp` + 条件跳 的错误返回形态。**
这一点与「50 个新函数是新面」的预期不符 —— 它们更像**编译器/运行时新增的辅助函数**（PAC 边界检查、原子位操作、断言），
而不是新的安全检查逻辑。

## 4. 没做的事（如实写）

1. **96 个 kext 的新函数没跑。** 预算用在了三次方法尝试上。工具已就绪：
   `python3 tools/newfuncs4.py --kext <name>`，粗键法可直接复用。
2. **4 个新导出名 ↔ 54 个函数地址的映射没做成。**
   `__LINKINFO` 的 `SymbolsSets` 每项只有 `{'SymbolName': '...'}`，**没有地址、没有序号对应**，
   顺序是字母序（`out/LINKINFO-NOTES.md` 已验）。**纯静态无法绑定。**
   `0xabbef50` 与 `_task_coalition_role_for_type` 的对应是**形态巧合级**证据，不成立为结论。
3. **54 个里体积 100–600 B 的**（父特别点名的那一档）只详读了 3 个。
