# 27.0.1 ↔ 27.2 全量差分：最终判定

对象：iOS 27.0.1 (24A446) vs 27.2，301 个 kext + `com.apple.kernel`
方法：逐函数反汇编 + 三层归一化 + 配对 delta 平移消除 + 字节级常量扫描
校准：`iokit_IOSurface` 的 `+0xf1` 三件套作为已知正例

---

## 1. 方法

### 1.1 差分流程

```
解 kernelcache（kseg.py）→ 按 LC_FILESET_ENTRY 切出 301 个 kext 切片
→ LC_FUNCTION_STARTS 枚举函数
→ 逐函数反汇编（capstone），三层归一化：
     a) mask adrp 页基址
     b) mask 紧随其后的页偏移
     c) mask 所有分支绝对目标 + >0xffff 的立即数
   保留：助记符、寄存器、小立即数、结构体字段偏移
→ 四分类：A 真插入（rem == []）/ B 布局位移 / C 行号漂移 / D 混合
```

### 1.2 污染源与消除（这是本方法的核心，不是附属）

| 污染源 | 现象 | 消除手段 |
|---|---|---|
| **桩↔实体错配** | 8 字节 `bti c; b <x>` 入口桩被拿去和真实函数体配对 | 配对前先 `follow_thunk()`，不跟桩配 |
| **体积悬殊** | 8 B 桩 vs 56 B 实体被当「改了」 | 尺寸比 >3× 直接拒绝配对 |
| **位域搬迁** | `ldrb [X,#a] + tbz #b` → `ldrb [X,#a+1] + tbz #0`，指令数不变 | 同助记符 + 同基址 + 仅偏移/位号变 → 判平移 |
| **栈写入当字段** | `strb` 到 `sp` 相对地址被当成结构体字段 | 排除 `sp` 相对偏移 |
| **重复 `bl` 当锁** | 「同一函数内多次调同一目标」被当 lock/unlock | 降级为弱信号 |
| **大改动混入** | 单函数 `add+rem > 40` 条被当一处改动 | 单列，不计强信号 |
| **结构体整体平移** | 见 §1.3，**最严重的一个** | 配对 delta 恒定 → 判负 |

### 1.3 结构体整体平移（本轮最大发现）

每个 kext 都有一条**恒定偏移 delta**，覆盖 46%–89% 的字段访问变化：

| kext | 偏移变化总数 | 主导 delta | 占比 |
|---|---|---|---|
| ApplePearlSEPDriver | 225 | **−3776** | 89% |
| lifs | 138 | **−304** | 89% |
| AppleSARService | 1729 | **+8** | 88% |
| apfs | 552 | **−1096** | 82% |
| AppleH16ANEInterface | 1519 | +8（其后 +16 占 30%） | 46% |
| AppleM2ScalerCSCDriver | 71 | +16（其后 +320 占 31%） | 49% |

**后果**：`fresh_off()` 那类「新偏移在旧版没出现过 ⇒ 是新字段」的判据**必然误报** ——
结构体整体挪 −3776 之后，新偏移确实没出现过，但旧偏移才是同一个字段。

**正确判据**：同一助记符 + 同一基址寄存器 + 偏移差恒定 ⇒ 平移，判负。

### 1.4 校准状态（必须写清楚）

- `IOSurface` 全程跑出 **2 条强信号**，正是已知的 `+0xf1` 配对，**未被任何规则误杀**。
- **但**「全库按形态签名扫描」（同函数内 strb + ldrb 同偏移）**没有命中 IOSurface** ——
  因为 `+0xf1` 的实际形态是**跨函数**的：一个函数写标记、另一个函数读门，同一字段。
  **⇒ 该形态扫描定义错误，其输出不作为结论依据。**（详见 §5）

## 2. 结论表：真改动只有两条

| kext | 27.0.1 地址 | 新增内容 | 分级 | 可达性 | 验证状态 |
|---|---|---|---|---|---|
| `iokit_IOSurface` | 读门 `0xa3460f0` / 写标记 `0xa34…` | 同一字段 `+0xf1` 上的「读门 + 写标记」配对，`0xE00002D8` 拒绝码 | **DoS**（已实测） | 有外方法 selector | **真机实测：5 次 panic，PC 全等** |
| `com.apple.kernel` | `0xb348450`（596 B） | 入口新增 `if ((0xC0 & ~w1) != 0) return 0xE00002C2`，即 `w1` 必须含 bit6/bit7 | **S** | **未定**（全镜像 0 调用者，见 §3） | 纯静态 |

其余全部归档为：**结构体平移 / 编译器 `udf` 断言 / 空指针守卫**。

### 2.1 为什么 kernel 那条不是平移

- `rem == []`（真插入、无配对对象可拿来算 delta）
- 新增块在**函数体之前**（独立校验前导块），不在原指令流里
- 596 B 全函数搜 `bic` / `#0xc0` ⇒ **零命中**
- 同一批的另外 2 条（`0xb2c2ff8` / `0xb2d0348`）经全量 diff 确认是 `ldp` 融合 + 一处无条件清 bit8，已降 B

## 3. 这批补丁「不是可挖面」的量化依据

```
批次 1–5 共 50 个 kext
强信号 102 条
形态分布：
   新增字节写标记      ~56   ← 主导 delta 证明绝大部分是平移
   新增字节读门        ~23   ← lifs 已证为 −0x130 平移
   udf / brk 断言        8   ← 编译器断言
   空指针守卫            4   ← ASIOKit，A 级防崩
   真新增前置检查         1   ← kernel 0xb348450
逐条复核过的平移样本：Pearl ×2（+0x140）、lifs ×1（−0x130）、SAR ×3（+8 / −0x28）
```

**⇒ 在这台设备可达的面上，27.2 相对 27.0.1 只有一个函数级真修复被定位到：
`com.apple.kernel 0xb348450`。加上已实测的 IOSurface `+0xf1`，共两条。**

### 3.1 `0xE00002D8` 聚类假设（父提出）—— 已否

```
27.0.1  1636 处 / 160 个 kext
27.2    1651 处 / 161 个 kext     净差 +15
```

`0xE00002D8` 在 27.0.1 里已有 1636 处，**是标准错误码，不是新标记**。
用它做「同类修复」的判别式在方法上不成立。

增量里唯一集中的是 `AppleSARService` +15（7 处 → 22 处，5 个函数 → 9 个函数）。
但逐条看那 3 个改动的函数对：两个 3460 B 同尺寸（`0x59c8→0x59d0`，+8），
一个 280 B（`0x308→0x2e0`，−0x28）—— **都是平移**。
`0xE00002D8` 构造点数上升本身**未定**（可能是内联展开，也可能是新校验，没逐点看）。

### 3.2 `__LINKINFO` 导出面（父提出）—— 基本没变

```
27.0.1  6146 个符号名
27.2    6150 个符号名
新增 4，删除 0，共有 6146
```

新增的 4 个：

```
_exclaves_indicator_system_state_change
_proc_coalitionids
_task_coalition_role_for_type
_vfs_context_allows_unmunged_atime
```

**导出面 +4/−0 ⇒ 27.2 没有删改任何 KPI，也没有新增对应 `0xb348450` 的名字。**
这解释了为什么 `0xb348450` 拿不到名字：**它是既有导出，不在差集里。**
（`_task_coalition_role_for_type` 的 "type" 参数与 `w1 & 0xC0` 形似，但**没有任何证据把它们连起来，不作推断**。）

## 4. 方法学教训（给后来者）

1. **`BIC`/`TST`/`ANDS` 这类位运算，先写真值表再下结论。**
   `bic w9, #0xC0, w1` + `cbnz → 拒绝` = 「`w1` **必须含** 0xC0」，不是「只允许 0xC0」。
   一个方向差，连锁作废两条推论。
2. **「对象是什么」看 `+0x00` 是不是 PAC 签名 vtable 且被 `autda` + `blraa` 调用。**
   是 → 内核 C++ 对象；否 → 再看字段布局。比按偏移猜可靠。
3. **任何「搜索返回 0」先用已知正例验方法。**
   本轮两次栽在这上面：数据段裸指针搜索（全是 chained fixups）、形态扫描未命中 IOSurface。
4. **桩↔实体错配**：8 B 的 `bti c; b` 入口桩不能和实体配对，否则凭空产生「插入」。
5. **体积悬殊拒绝**：尺寸比 >3× 不配对。
6. **配对 delta 判平移**：不要问「这个偏移出现过没有」，要问「配对的两条指令偏移差是否恒定」。
7. **`movz` 会被 capstone 显示成 `mov`。** 做指令形态匹配时按编码或同时接受两个助记符，
   否则会得到「全库零命中」这种假阴性。

## 5. 明确标注为「方法不成立」的两项

1. **全库三件套形态扫描**（`tools/triple_scan.py`）：
   定义为「同一函数内同时有 `strb` 写标记和 `ldrb` 读门在同一归一化偏移」。
   **IOSurface 的已知正例不命中** —— `+0xf1` 是**跨函数**配对（一个函数写、另一个函数读）。
   ⇒ 扫描定义错误，输出（ANEInterface 43、SAR 38、AGX 22…）**不作为结论**。
2. **`fresh_off()` 规则**：见 §1.3，在全局布局变动下必然误报，已由配对 delta 取代。
