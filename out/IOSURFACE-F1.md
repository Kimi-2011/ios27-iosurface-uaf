# IOSURFACE-F1 — `obj+0xf1` 守卫：注册 / 注销的重复操作

README
1. 27.2 的 IOSurface 只改了两个函数（`#799` `0xa3944c0`、`#802` `0xa394744`；27.0.1 对应 `0xa3460f0`、`0xa346364`）。
2. 1,330 个函数按序号对齐、1,328 对长度全等，锁类桩调用 162/179/70/9 两版完全相同，**新增原子/锁指令 0**。
3. 改的不是锁，是**新增标志字节 `obj+0xf1`**：`#802` 置 1，`#799` 检查后拒绝。
4. `#799` = 把节点**注册**进 `[reg+0x188]` 链表；`#802` = 把节点**注销**并释放。
5. `0xb32a1ac` 分配 / `0xb32a3a8` 释放，两者相邻（差 `0x1fc`），是同一 zone 的一对。
6. 已有检查 `0xE00002C9` 只挡「同一个 key 还在链表里时再注册」；注销后链表里已无该节点，所以**挡不住注销后重注册**。
7. `0xf1` 在整个 kext 里只有这两处访问 → 它纯粹是给 `#799` 用的「已注销」标记。
8. **可达（注册侧）**：`0xa3498f4` 是 **selector 17 的 handler**，它尾调 `#799`。
9. **没证据的部分**：注销侧调用者 `0xa34b2dc` 不在 selector 表里，`destroy(node+0x10)` 具体释放什么未读，**不声称 UAF**。
10. 以下每条都手读；自动扫描只用来提供候选。

## 1. 两个函数的完整语义（逐条手读）

### `#799`（27.2 `0xa3944c0`，69 条）= 注册节点

```
x19=self(注册表)  x23=x1  x22=x2  x21=x3   w20=0xE00002BD
lock(self+0x150)                                   ← stub→0xac2475c
[NEW] ldrb w8,[x21+0xf1]; tbz w8,#0 → 继续
      add w20,w20,#0x1b → 0xE00002D8; goto 收尾      ← 27.2 才有

                                                   ← 原有检查：还在表里就不许再插

### `#802`（27.2 `0xa394744`，59 条）= 注销节点并释放

```
x19=self(注册表)  x20=x1(要注销的 key)
lock(self+0x150)

## 2. `+0xf1` 属于哪个对象

| 偏移 | 用途 | 证据 |
|---|---|---|
| `+0xe8` | 注册表对象（`#799`/`#802` 的 self 就是从它来的） | handler 都做 `x0 = [self+0xe8]` 再尾调 |
| `+0xf0` | **标志字节 bit0**：注销前先检查，登记后清 0 | `0xa34b2dc`：`ldrb w8,[x0,#0xf0]; tbz w8,#0 → 跳过整段注销` |
| `+0xf0..0xf3` | 注销时整字清 0 | `sturb wzr,[x21,#-8]`（x21 = obj+0xf8 → 打到 +0xf0） |
| **`+0xf1`** | **27.2 新增：已注销标记** | 本文两个函数，全 kext 只此 2 处访问 |
| `+0xf8` | PAC 签名的指针（注销时 `autda`+`xpacd`+校验，失败 `brk #0xc472`） | `0xa34b2dc` |

注意顺序：注销路径**先**把 `+0xf0` 整字清 0，**再**调 `#802` 置 `+0xf1 = 1`。所以 `+0xf1` 是清标志之后唯一留下的痕迹——这是有意为之，不是巧合。

**这里推翻我自己一处**：上一轮我说「`#799` 没有直接调用者」。那是扫 `bl` 的漏——它被 **`b` 尾调**两处。判据纪律里「一层 `bl`」的缺陷，这是第二次咬到。

## 4. 直答

**`+0xf1` 守卫防的是什么重复操作？**
防「**已经注销过的 IOSurface 再走一次注册**」。注册时链表里要插一个节点，节点 `+0x58` 存这个 surface；注销时节点被 `destroy(node+0x10)` + `free(node)`。原有的 `0xE00002C9` 只在「节点还在链表里」时拦重复注册；**注销之后链表里已经没有该节点，所以那道检查拦不住**。27.2 因此额外在 surface 上留一个 `+0xf1=1` 的标记，注册前先看一眼。

**27.0.1 里能重复做吗？**
**能。** 27.0.1 的 `#799` 没有 `ldrb/tbz` 这两条，`#802` 也没有 `strb`。所以「注销 → 再注册」在 27.0.1 上是完全放行的，且注册会成功（返回 0）。

**后果是 UAF 还是别的？**
**机制清楚，但最终被释放的对象没读到，所以不声称 UAF。** 能证实的：重新注册会给一个已注销的 surface 挂上一个**新节点**，节点 `+0x10` 用当次的 `x1/x2` 初始化，`+0x58` 指向该 surface。此后任何一次注销都会对这个新节点执行 `destroy(node+0x10)` + `free(node)`——**而 `destroy` 作用在一个其宿主 surface 已被注销过的节点上**。`destroy(node+0x10)`（`0xb3d115c`）内部释放什么，**我没读**，这是「是 UAF 还是泄漏/断言」的分界点，留白。

**从 type=0 的哪个 selector 能触发？**
注册侧：**selector 17**（`0xa3498f4`，`out/census.json` 里 IOSurface 第 18 行，`handler=0xfffffe000a3498f4`）。用户态 `IOServiceOpen(IOSurface, type=0)` 后按 selector 17 调用即可到达 `#799`。注销侧：调用者 `0xa34b2dc` 不是 selector handler，往上还有一层没追，**可达性未证**。

## 5. 射程

1. 注销侧（`#802`）的可达路径没有追到 handler；`0xa34dbc0` 这条 `#799` 入口也没追。
2. `destroy(node+0x10)` = `0xb3d115c` 的内部行为未读 —— 「UAF / 泄漏 / 断言」三者未定。
3. 节点结构只读出 `+0x00 next`、`+0x08 prev`、`+0x10 子结构`、`+0x20 与 x2[8] 比对`、`+0x50 = x2[0x10]`、`+0x58 = surface`，其余字段未读。
4. 27.2 只比 27.0.1 多这一个守卫，IOSurface 其余 1,328 个函数逐对无原子/锁指令变化。
