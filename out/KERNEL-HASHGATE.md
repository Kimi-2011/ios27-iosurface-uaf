# com.apple.kernel：27.2 新增的「哈希门」校验（5 处）

> 起点：`out/KERNEL-137-TRIAGE.md` 里 37 个「未定性」中 #33/#34
> （`0xacc5164` / `0xacc52c8`，标注「共享完全相同的 49 条插入序列」）。
> 本文件是对该插入序列的定性。

## 1. 插入序列原文（27.2 `0xad16b8c` 起）

```asm
adrp x8, #0xfffffe0007dfd000
ldr  x8, [x8, #0x6a0]        ; 全局指针
cbz  x8, <skip>              ; 为空则跳过整套校验
adrp x9, #0xfffffe000b770000
ldr  w9, [x9, #0x2c0]        ; 全局标志
cbnz w9, <other>             ; 非零走另一条
eor  x9, x20, x20, lsr #31   ; 对 x20（对象指针）做混合
mov  x10, #0xa185
movk x10, #0x728e, lsl #16
movk x10, #0xd329, lsl #32
movk x10, #0x7fb5, lsl #48   ; 常量 0x7fb5d329728ea185
mul  x9, x9, x10
eor  x9, x9, x9, lsr #27     ; 乘法-异或散列
```

**形态：对对象指针做 64 位乘法-异或散列，用全局表 + 全局标志门控。**
这是**对象身份/类型校验**，不是长度检查，也不是空指针检查。

## 2. 规模：363 → 368，只多 5 处

用 `mov x10, #0xa185` 的指令字 `0xd29430aa` 全库计数：

```
27.0.1: 363 处
27.2  : 368 处
全部位于 com.apple.kernel（无一处落在其它 kext）
```

**⇒ 这个机制原本就存在（27.0.1 已有 363 处），27.2 只新增了 5 处。**

**5 处是修补特定缺陷的典型规模，不是全局加固。**

## 3. 为什么这条值得追

- **不是**「改动大所以可疑」——只有 5 处
- **不是**功能新增——插入的是校验门控
- **是** Apple 在一批既有校验点之外，额外补了 5 个位置
- 且这 5 处**不在 159 个候选的已定性集合里**（#33/#34 属「未定性」）

**结合 `KERNEL-137-TRIAGE.md` 的净结论「S2 仍缺」，这 5 处是内核侧最后一个未解释的新增校验。**

## 4. 下一步（有界）

1. 精确列出这 5 个新站点的 VA（当前已知其一 `0xfffffe000ad16ba8`，位于 #33 函数内）
2. 每个站点往前找函数起点，确认它属于哪个子系统（靠邻近字符串或调用者）
3. 判断 `x20`（被哈希的对象）**是否可能由用户输入决定**
4. 若某处对象来自用户可控路径 → 27.0.1 缺这一步校验，是类型混淆/UAF 的候选

## 5. 已知的坑（勿重复）

- 不能用「常量出现次数多」推断全局加固——**必须减去旧版基线**（363 是基线，5 是增量）
- 不能用位置直接配对跨版本 VA（`KERNEL-137-TRIAGE.md` §4 已证伪两例）
- `bl 0xadac744` 在全库只 2 次（`AppleSARService` + `com.apple.kernel`），不能据此推断校验规模；
  规模要看**内联后的散列常量**，不是调用

## 6. 五个新站点已定位到 4 个（签名法 + LC_FUNCTION_STARTS）

**方法**：取站点前 10 条指令的助记符序列作为签名，在 27.0.1 的 363 个站点签名里查存在性。

```
27.2 站点 368 个；签名在 27.0.1 找不到的 = 4 个
```

| 站点 VA | 所属函数（LC_FUNCTION_STARTS 权威边界） | 函数内偏移 | 形态 |
|---|---|---|---|
| `0xfffffe000acdb544` | `0xfffffe000acdb260` | +0x2e4 | 纯内联散列 |
| `0xfffffe000ad16ba8` | **`0xfffffe000ad16ae4`** | +0xc4 | **带全局门控** |
| `0xfffffe000ad16dd4` | **`0xfffffe000ad16d18`** | +0xbc | **带全局门控** |
| `0xfffffe000b296678` | `0xfffffe000b2960c8` | +0x5b0 | 纯内联散列 |

**关键**：`0xad16ae4` / `0xad16d18` **正是 `KERNEL-137-TRIAGE.md` 里的 #33 / #34**
（`0xacc5164 → 0xad16ae4`、`0xacc52c8 → 0xad16d18`），
也就是文档标注「共享完全相同的 49 条插入序列」的那一对。**两处都已确认是散列门。**

## 7. 调用者扫描（用于识别子系统）

```
#33 0xad16ae4 : 0 个直接 bl 调用点
#34 0xad16d18 : 0 个直接 bl 调用点
A   0xacdb260 : 2 个（0xacd0e0c、0xacd9bec）
B   0xb2960c8 : 3 个（0xb28754c、0xb287bf4、0xb297adc）
```

**#33/#34 零直接调用点 ⇒ 只能经间接分派进来（虚表 / 函数指针 / externalMethod 槽位）。**

这条对可达性判断很关键：间接分派的槽位如果对应某个用户可触发的操作，
那两个散列门就是"给用户可达路径补的身份校验"。
