## 0. 三句话结论

1. **三个「像 IOVA 的返回值」没有一个能由入参控制，也没有一个是自身地址的回显。** 两个是**单调时钟读数**（`mach_continuous_time()`），一个是**我们自己进程里的一个只读映射地址**（用户 VA，内容全零）。
2. **MFB 47 个 selector 里 25 个拿到 `kr==0`**；另 22 个的入参契约也全部解出来了，只是 handler 内部返回错误（`NotPrivileged` / `NotAttached` / `Busy` / `kIOReturnError` / `KERN_INVALID_ADDRESS`）。
3. **`structOut` 通道是空的**：47 个 selector 中**没有任何一个**接受 `sst>0` 并写字节；25 个成功 selector 的输出**全部是标量**。全程 **0 个内核 VA**，**0 次 panic**，**0 次超时**。

## 1. 三个「像 IOVA 的返回值」的全部观测

### 1.1 三个目标与它们的基线契约

上一轮 `SVC-REENUM.md` 用容量阶梯在 `(soc=1, sst=0)` 下撞出的三个标量输出：

```
IOSurfaceRoot       sel 32  -> 0x0000000102c48000
IOMobileFramebuffer sel 77  -> 0x00000030aec27220
AppleCLCD2          sel 77  -> 0x00000030b8f8b1a8
```

本轮先确认：这三个 selector 的**唯一合法契约**就是 `(sinCnt=0, sti=0, soc=1, sst=0)`。

### 1.2 同一进程内连续调用 3 次 / 双连接（`@iova`）

`stage iova`，每个服务开 **两个** `IOServiceOpen`（`c1`/`c2`，都 `SUCCESS`）。

| 服务 | sel | rep1 | rep2 | rep3 | conn2_rep1 | conn2_rep2 | after_others | after_close2 |
|---|---|---|---|---|---|---|---|---|
| `IOSurfaceRoot` | 32 | `0x105060000` | `0x105060000` | `0x105060000` | `0x105060000` | `0x105060000` | `0x105060000` | `0x105060000` |
| `IOMobileFramebuffer` | 77 | `0x34b3ec417e` | `0x34b3ec463a` | `0x34b3ec4a81` | `0x34b3ec4e3d` | `0x34b3ec51ae` | `0x34b3ed0e54` | `0x34b3ed3f18` |
| `AppleCLCD2` | 77 | `0x34b3ed5dbf` | `0x34b3ed6eda` | `0x34b3ed7127` | `0x34b3ed75d1` | `0x34b3ed8fdf` | `0x34b3ee2ea0` | `0x34b3ee4870` |

**读法**：

- `IOSurfaceRoot sel 32` —— **同进程内恒定**，两个连接拿到**同一个值**，中间插入 5 个别的 selector、关掉第二个连接都不影响。
- `MFB sel 77` / `CLCD2 sel 77` —— **每次调用都变，严格单调递增**，与用哪个连接无关（c1/c2 交替时序列仍连续）。`after_close2` 那两发跨服务的增量（`0x34b3ee2ea0 - 0x34b3ed8fdf = 0x9ec1`）恰好覆盖其间的 20 发取样 + 一次 `IOServiceClose`，说明这个量是**随时间走**的，不是被调用次数走的。

### 1.3 入参扫描（27 组 / 每服务）

| 入参改动 | `IOSurfaceRoot` 32 | `MFB` 77 | `CLCD2` 77 |
|---|---|---|---|
| `sinCnt=1`，值 `0 / 1 / 2 / 3 / 0x100 / 0xFFFF / 0x1_0000_0000 / 0xDEADBEEF_CAFEBABE` | 全 `0xE00002C2` **未写** | 同左 | 同左 |
| `sinCnt=1`，值 = **我们自己 mmap 的页地址**（`0x104f70000`） | `0xE00002C2` 未写 | 同左 | 同左 |
| `sinCnt=2` (`1,2`) / `3` (`1,2,3`) / `4` (全 `0xFFFFFFFF`) | `0xE00002C2` 未写 | 同左 | 同左 |
| `sti = 8 / 64 / 4096`（0xA5 填充，哨兵校验） | `0xE00002C2`，`s8=1` | 同左 | 同左 |
| `soc = 2 / 4 / 8`（预填容量） | `0xE00002C2` | 同左 | 同左 |
| `sst = 64 / 4096`（预填容量） | `0xE00002C2`，`s8=1` | 同左 | 同左 |

**`soc` 必须恰好等于 1**：给 2/4/8 一律 `BadArgument`。这是这三个 selector 契约最硬的一条。

> **结论**：入参一个比特都影响不到返回值。**没有触发任务书里「值能被入参改变 / 像是我们指定地址的回显 ⇒ 立刻停下汇报」的判据。**

### 1.4 机制定性 —— 它们到底是什么

#### 1.4.1 `MFB sel 77` / `CLCD2 sel 77` = `mach_continuous_time()`

`stage iova3`：每次调用前后各取一次 `mach_absolute_time()`（`t0/t1`）与 `mach_continuous_time()`（`ct0/ct1`），再与返回值 `v` 比。

| 判据 | `IOMobileFramebuffer` 77 | `AppleCLCD2` 77 |
|---|---|---|
| `v` 落在 `[ct0, ct1]`（continuous 时钟窗口）内 | **12 / 12** | **12 / 12** |
| `v - ct0`（ticks） | 366 – 6 596（窗口宽度约 900–7 000 ticks） | 同量级 |
| `v - mach_absolute_time()` | **常量 ≈ +15 829 6xx xxx ticks**（≈ 659 s） | 同左 |

- 常量偏移 ≈ 659 s = 开机以来累计休眠时间 ⇒ 它跟着**含 sleep 的时钟**走，不是 `mach_absolute_time()`。
- 增量率核对：`Δv / Δ(ns) = 0.024 ≈ 1/41.667`，即 **24 MHz debug 时钟的 tick 率**；取样点 `Δv = 1154 ticks` 对应 `Δwall = 48 000 ns`，预测 `48 084 ns`，吻合。
- timebase 实测 `numer=125 / denom=3`。

**判读：这是时间戳（uptime incl. sleep 的 tick 计数），不是地址、不是 IOVA、不是对象句柄、更不是内核 VA。** 信息价值仅限「知道开机多久」。

#### 1.4.2 `IOSurfaceRoot sel 32` = 我们自己 task 里的一个 16 KiB 只读映射

`stage iova3` 对返回值直接做 `vm_region_64` + `vm_read_overwrite`：

| 字段 | 实测值 |
|---|---|
| `v` | `0x0000000100c54000`（本进程；同日另两次运行分别是 `0x102c48000` / `0x105060000`） |
| `vm_region` 是否认领且 `start == v` | **是** |
| `size` | **`0x4000`（16 KiB）** |
| `protection` / `max_protection` | **`1` / `1`（只读，不可写）** |
| `share` | `0` |
| `inheritance` | `2` = `VM_INHERIT_NONE`（内核为我们建立的一次性映射） |
| `vm_read_overwrite` 256 B | **`KERN_SUCCESS`，`got=256`，内容全 `0x00`** |

- 同进程 12 发（两个连接交替）**恒定不变**；跨进程每次不同（`0x102c48000` → `0x105060000` → `0x100c54000`）⇒ **每进程独立分配的映射**，不是全局固定 IOVA（它没有随重启变化就已排除全局 IOVA；它在同一次开机里换了三次）。
- 值域落在用户空间（`0x0000000X_xxxxxxxx`，`X=1`）。

**判读：用户 VA，指向内核 map 进本进程的一块 16 KiB 只读零页。因为它就在我们自己的地址空间里，不构成信息泄露。** 可读、只读、不可写，前 256 B 全零。

#### 1.4.3 高位规律 —— 为什么两个量级差这么多

| 值 | 位宽/对齐 | 归属 |
|---|---|---|
| `0x0000000102c48000` / `0x0000000105060000` / `0x0000000100c54000` | 40 bit，**4 KiB 页对齐** | 用户 VA（本进程映射地址），页对齐是因为映射必页对齐 |
| `0x00000030aec27220` / `0x00000034b3ec417e` / `0x00000035b7465d55` | 38–40 bit，**不对齐**（尾数随机） | 24 MHz 时钟 tick，低位随机是取样时刻造成 |

「量级差很多」不是「一个 IOVA 一个句柄」，而是**两个完全不同的类别**：一个是地址（必然页对齐），一个是计数器（必然不对齐且单调）。

> 补充：`0x30aec27220` 加上 `0xfffffe` 前缀确实能拼成 `0xfffffe30aec27220` 这种「看起来像内核 VA」的形状 —— 这是**巧合**，不是截断。判据在 1.4.1：它的增量率等于 24 MHz 时钟，且落在 `[ct0, ct1]` 窗口内 12/12。地址不会以时钟速率单调递增。

## 2. MFB 47 个 selector 的成功契约表

### 2.1 怎么找的

`stage ct`：`IOMobileFramebuffer` type 0，`IOServiceOpen` → `SUCCESS`。先用 sel `0,1,2,3` 各一发预热，然后对 47 个 selector 逐一跑组合网格：

```
sinCnt ∈ {0, 1, 2, 3, 4}
sti    ∈ {0, 8, 64, 156, 664, 1760, 3084, 4096}     // structIn 长度，全 0 填充 + 4096 上限（MIG 硬限）
soc    ∈ {0, 1, 2, 4, 8}                            // scalarOut **预填容量**
sst    ∈ {0, 64, 4096}                              // structOut **预填容量**
```

- 迭代序 = 上表从左到右嵌套（`sin` 最外、`sst` 最内），**命中即停**（该 selector 第一个 `kr==0` 就收）。
- 每发都重新预填 `soc`/`sst` 容量并把 `sout`/`bst` 灌哨兵（`0xA5A5…` / `0x5A`），避免「上一发的输出被当成本发的」。
- 单次调用 3 s 超时；同一 selector 连续 2 次超时即跳过该 selector。
- 额外记录 **`@touch`（擦边）**：返回码离开 `0xE00002C2`/`0xE00002C7` 就说明**入参校验过了、handler 真跑了** —— 这样即使没 `SUCCESS`，也能把契约形状解出来。这条是本轮把「未成功的 22 个」也全部解出契约的关键。

**实测代价**：47 个 selector、上限 28 200 组，因为命中即停实际只打了 **15 112 发**，耗时 **265 ms**，**0 超时**。

## 3. `kr==0` 的 dump 与指针判读

### 3.1 `structOut` 通道：空的（这是本轮的一个重要否定结果）

`stage dump` 对 25 个成功 selector，用**最大预填容量**重跑容量阶梯：

```
soc ∈ {1, 2, 4, 8, 0}   ×   sst ∈ {4096, 64, 0}
```

取 `(oc + sc)` 最大的那个 `kr==0` 组合再 dump（最多 512 B，16 字节一行）。

**结果：25 个 selector 全部选中的是 `sst=0`。** 具体地：

| 观测 | 数值 |
|---|---|
| `sc > 0`（内核声称写了 structOut 字节）的成功调用 | **0 / 25** |
| `s8 == 1`（structOut 哨兵 `0x5A` 全未被改写） | **25 / 25** |
| 触发 hexdump 的 `@h` 记录 | **0 条** |
| `@w8` / `@w4` / `@ptr` 记录（structOut 上的对齐指针扫描） | **0 条** |

也就是说：**hexdump 无内容可给 —— 因为没有任何一个 selector 往 `structOut` 写过字节。** 任务书里那条判据「37 个新 selector 里有 `kr==0` 且 `sst>0` ⇒ 新输出通道」**没有成立**：在这套网格（`structIn` 全 0 填充）下，MFB 的输出面**只有标量**。

（`@h` 一条都没有不是 bug：`dump_job()` 只在 `sc>0 && 哨兵被改写` 或哨兵被改写时才吐 hexdump；两者都没发生，于是只记 `@zero` / `@so`。）

### 3.2 标量输出的完整读法（8 字节对齐 + dword 双视图）

严格按 **8 字节对齐**（`off % 8 == 0`）读，同时给 **4 字节对齐**（`off % 4 == 0`）的 dword 视图对照。25 个成功 selector 里 13 个产生标量输出（`@so` 14 条，`sel 8` 一条里有 2 个标量），其中 **7 个非零**：

| selector | 8 字节对齐（LE qword） | 高位判读 | dword 双视图（`off 0 / 4`） | 结论 |
|---|---|---|---|---|
| 4 | `0x000000000000000a` | 无高位 | `0x0000000a` / `0x00000000` | 普通小整数（10） |
| 7 | `0x0000000000000001` | 无高位 | `0x00000001` / `0x0` | 普通小整数 |
| 8 | **两个独立标量**：`i=0 → 0x492`，`i=1 → 0x9e4` | 无高位 | 同左 | **`0x492=1170`、`0x9e4=2532`，宽高对**；见 §3.3 |
| 14 / 18 / 25 / 91 / 92 / 98 | `0x0000000000000000` | 无高位 | 全 0 | 0 |
| 49 | `0x0000000000000001` | 无高位 | `0x1` / `0x0` | 1 |
| 77 | `0x00000034b3ec417e`（每发不同） | `hi40_unaligned`，最高字节 `0x00` | `0xb3ec417e` / `0x00000034` | **不是指针**，是 §1.4.1 的时钟 |
| 80 | `0xffffffffffffffff` | `very_high`，但**全 1** | `0xffffffff` / `0xffffffff` | **−1，被显式排除**，不是指针（沿用旧轮判据） |
| 82 | `0x0000000000000007` | 无高位 | `0x7` / `0x0` | 7 |
| 12 / 13 / 19 / 22 / 26 / 31 / 33 / 51 / 53 / 56 / 81 / 88 | 无标量、无 struct | — | — | 纯动作型，`@zero` |

**分类统计（25 个成功 selector）**：

- 普通小整数（`< 4096`）：**5 个** selector（`sel 4 = 10`、`sel 7 = 1`、`sel 8 = 1170+2532`、`sel 49 = 1`、`sel 82 = 7`）
- 常量 0：**6 个** selector（`14 / 18 / 25 / 91 / 92 / 98`）
- 完全无输出（纯动作型）：**12 个**
- `0xffffffffffffffff`（−1）：1 个（sel 80）
- 时钟 / 计数器：2 个（MFB 77、CLCD2 77）
- **用户 VA（`0x0000000X_xxxxxxxx`）：0 个**（唯一的那个在 `IOSurfaceRoot sel 32`，见 §1.4.2）
- **IOVA：0 个**
- **内核 VA（`0xfffffe..`）：0 个**

### 3.3 `sel 8` 就是「8 字节窗口把两个 32 位字段拼成假指针」的活标本

`sel 8` 声明 `soc=2`，内核写回**两个独立标量**。如果按 8 字节对齐把它们当**一个 qword** 读，会得到：

```
[0x000009e4][0x00000492]  ->  qword = 0x000009e400000492   (≈ 2.7e12)
```

这个值 `>= 4 GiB` 且 `hi40_page`，按上一轮的粗判据会被错标成「疑似用户 VA / IOVA」——**实际是两个 32 位宽度值（1170 × 2532）被窗口拼起来了**。

这就是为什么本轮的判读一律要求**同给 dword 视图**：`0x492` 与 `0x9e4` 分别落在 `off 0` 和 `off 4`，一眼就能看出是「两个字段」而不是「一个 64 位地址」。同理，旧轮出现过的 `0x0000feff` 被 8 字节窗口读成 `0xfffe…` 的假象，在 dword 视图下会立刻散架。

## 4. ★ 有没有出现内核 VA —— 单独一节

**没有。**

| 检查项 | 覆盖范围 | 命中 |
|---|---|---|
| 8 字节对齐 `0xfffffe..`（arm64 内核线性映射） | 全部 5 个 stage、**17 000+ 发调用**的 `structOut` 全 4096 B 扫描 + 每个标量输出 | **0** |
| 8 字节对齐 `0xffffff..` | 同上 | **0** |
| 最高字节 `>= 0xF0`（带 PAC 的高位标签） | 同上 | **0**（`sel 80` 的 `0xffffffffffffffff` 被 `scan_ptr64()` 显式排除为「写了个 −1」） |
| 用户态直接读回来的 16 KiB 页（`IOSurfaceRoot sel 32`）里是否有内核指针 | 前 256 B 的 `@uw8` 扫描 | **0**（内容全零） |
| `extmethod` 返回码里 `0x1` / `0xE00002..` 之外的可疑值 | 47 selector × 2 112 发 | 仅 `sel 89` 的固定 `KERN_INVALID_ADDRESS`，已证伪与地址无关（§2.3） |

`stage dump` 结尾的 `@done` 里 `kv_hits` 字段（内核 VA 命中计数器）在 **iova / iova2 / iova3 / ct / ct2 / dump 全部 6 次运行里都是 0**。

**结论：本轮 MFB 面没有内核信息泄露。** 唯一「看起来像指针」的 `0xffffffffffffffff` 是 −1；唯一真正的地址是**我们自己进程**的一个只读零页。

## 7. 边界、没做的事、下一步建议

**严格按任务书边界执行**：只做了这 8 个服务里的 3 个（`IOSurfaceRoot` / `IOMobileFramebuffer` / `AppleCLCD2`）的 sel 32 / 77 / 77 与 MFB 的 47 个 selector；**没跑竞态、没碰 `harness/israce/`、没改 `out/` 既有文件**、没 `git`、没重启设备。

**明确没做的两件事**：

1. **没向任何 selector 喂内核态地址向量**（`>= 0xFFFF000000000000`）。理由见 §2.3：用户态地址已足够证伪「地址回显」，而喂内核地址有打死设备的风险，与「不重启设备 + panic 保持 5」冲突。若后续在**独立进程 / 独立 stage** 里愿意承担一次 panic，`sel 89` 是唯一值得试的那个（形态与 M2Scaler sel 7 一致）。
2. **`structIn` 一律 0 填充**。`sel 56` 的 156 字节只证明了「长度对」，没证明「内容要什么」。`sel 12/13/19/22/31/33/51/53/81/88` 这些纯动作型 selector 只证明了「不给输出也能成功」，它们在**语义正确**的标量入参下是否会产生输出，本轮没测（网格的 `sin` 值固定为 0）。

**下一步最有价值的三个方向**：

| 优先级 | 方向 | 依据 |
|---|---|---|
| 高 | `IOSurfaceRoot sel 32` 那个 16 KiB 只读页**在什么条件下才会变**（例如先 create 一个 surface） | 它现在是全零的只读页；若某条路径能让它被填充，就是一个可控的 kernel→user 数据通道 |
| 中 | `sel 59–65 / 70 / 71` 那 9 个 `NotAttached` | 它们只差一个 attached 的显示对象；接上外接屏 / 让 app 上屏后可能全部点亮 |
| 中 | `sel 86 / 100` 的 `NotPrivileged` | 需要 entitlement；值得比对 `out/ents.plist` 里现有条目与它们可能要求的 key |
