## README（10 行摘要）

1. **结论：137（修正口径 159）个候选里没有找到 app 沙箱可达的内核内存破坏原语。** 内核侧 S2 这一环仍然缺。
2. 找到 **2 个真补丁**，都不是内存破坏：`bindfs` 的 vnode 类型门（需 mount 权限，app 不可达）；TCP 选项长度 ≥4 校验（访问已被现有边界检查覆盖）。
3. **「137」这个数字本身是错的**：函数边界规则少切了约 6800 个函数（见 §2.1）。修正后是 **159**。
4. **按位置配对的 137 个里含大量假象**：换成锚定配对后两个独立方法都得到 **129**，且完全一致；已被证伪的两例（`0xacfaf88→0xad4cce0`、`0xae8a4b8→0xaedd7c0`）在新口径下**直接消失**。
5. **dChk 本身还有一个失效模式**：基本块重排会把「同一个分支」数成「新增分支」（见 §2.3）。所以本轮引入「校验签名多重集差分」作为判据，dChk 只当闸门。
6. 159 个里：功能新增 **56**、防御加固 **38**、重构/内联/重排 **19**、假配对/合并待查 **5**、可疑 **2**、真补丁 **2**、未定性 **37**（合计 159）。除 15 个 `✔人工` 外均为签名级自动定性。
7. **人工逐条反汇编确认的只有 15 个**（占 9.4%）。§7 明确列出没看的清单，不伪造覆盖率。
8. 顺带解决一个历史悬案：`CHAIN-DESIGN.md` §5 里被 KDK 猜成 `null_getnewvnode` 的那个函数，**字符串锚点是 `bindfs`**，与 `/dev/null`、`nullfs`、`devfs` 全都无关。
9. 附带修正 `METHOD-FUNCTION-BOUNDARY.md`：新增第 3、4 两条缺陷，给出一条经 6807/6807 验证的边界规则。
10. 全部工具与中间数据在 `/tmp/kpair.py` `/tmp/kfix.py` `/tmp/ksig.py` `/tmp/k137/`，可复算。

## 2. 三处方法缺陷（本轮新增两条）

### 2.1 缺陷三：函数边界规则少切约 6800 个函数（已量化证实）

`/tmp/dchk2.py` 的规则要求 `BTI c`/`PACIBSP` 的**前一条**是 `ret/retab/nop/跳转`。但实测：

```
kern.27.2 __TEXT_EXEC 内 pacibsp 总数 16498
按规则被认作起点           9691
"函数体内"残留 pacibsp     6807
其中后接 prologue 的        6807  (100%)
    sub/add sp, sp, #imm   3974
    stp/str ..., [sp...]   2829
    mov                    4
```

**6807 个残留 `pacibsp` 无一例外后面紧跟栈帧建立指令** —— 它们是真实函数起点，只是前一条是 `bl`（调用 noreturn 助记如 `panic`/`__assert_rtn`）或 `brk`（`brk #0` 陷阱后）。

后果：相邻函数被合并成一个「函数体」，指令数与 dChk 一起虚高。实例（旧口径下排名第一）：

```
0xabc6850 (470 条) ← 实际是 2 个函数
0xac17788 (758 条) 内部 0xac178a0 处有 pacibsp，前一条是 bl
```

修正规则（已验证：23277 个起点，`bti`-only 的 6821 个也全部后接 prologue 或 `br`/`ret` 桩）：

```
起点 = 任一 PACIBSP
      ∪ (BTI c 且下一条 != PACIBSP)
```

工具：`/tmp/kfix.py`（本轮的边界与签名实现）、`/tmp/kpair.py`（旧边界锚定版，留作对照）。

### 2.2 缺陷四：dChk 会把「搬走的分支」算成「新增的分支」

实测正例（`0xaef4690 → 0xaf48310`，dChk=+5）：

```
27.2 新增侧: cmp x8, #0xc ; b.hi  ×2
27.0.1 删除侧: cmp x8, #0xc ; b.hi  ×2      ← 完全同一对
```
两个分支只是被基本块重排/循环倒装挪了位置，条件、立即数、目标全部等价。**净语义变化为 0，但 dChk=+5。**

因此本轮把判据换成**校验签名多重集**：把每条条件分支规约为
`(比较操作, 分支条件, 操作数形状[寄存器只留宽度, 保留立即数与字段偏移], 被比较寄存器)`
然后做 `Counter(B) - Counter(A)`。寄存器重命名（`w25↔w24`）、块重排、立即数地址变化都不会产生假签名。

- 159 个候选里，**15 个的净新增签名 = 0** → 纯重排/重命名，直接归为「重构」。
- 剩下 144 个的净新增签名分布：最大 +49，中位 +2。

工具：`/tmp/ksig.py`（`python3 /tmp/ksig.py all` 出全量排序，`python3 /tmp/ksig.py A_VA B_VA` 出单对）。

### 2.3 缺陷五（本轮踩的坑，第五次同类）：哈希运算长得像边界校验

`0xacc5164 → 0xad16ae4`（dChk=+6，且两个函数共享**完全相同**的 49 条插入序列）在签名级看起来是：

```
+ CMP lo x,x     （x2 与 x8 比较 → 像单侧下界）
+ CMP hs x,x     （x8 与 x22 比较 → 像上界）
```

逐条读完才发现整段是**乘异或哈希表查找**：

```asm
eor  x9, x20, x20, lsr #31
mov  x10, #0xa185 ; movk ... 0x7fb5      ; 64-bit 乘法常数
mul  x9, x9, x10
eor  x9, x9, x9, lsr #27
mul  x9, x9, x10                          ; （第二组常数 0x81da_bc2d_d44d）
and  w9, w10, w9                          ; w10 = 表容量-1
ubfiz x10, x9, #5, #0x20                  ; ×32 槽位
cmp  x10, w10, sxtw                       ; ← 这句不是边界检查，是符号扩展比较
ldrh w8, [x9, #0xa]
and  w10, w8, #0xff
cmp  w10, w8, lsr #8                      ; 高低字节相等 → "槽位有效"标记
b.ne fail
```

而且 **27.0.1 的这个函数只有 44 条，`str xzr,[x19]` 直接返回空** —— 它是个空桩，27.2 才写出真实实现。
→ 定性：**功能新增（空桩→实现）**，与边界校验无关。

这就是「形式特征当语义证据」的第五例。记在这里，下次再看到 `cmp xN, wN, sxtw` 不要兴奋。

## 4. 两个真补丁：完整数据流与派发入口

### 4.1 `bindfs` 的 vnode 类型门（该工程此前的旗舰候选）

**27.0.1 `0xfffffe000b1b4624`（76 条）→ 27.2 `0xfffffe000b20a528`（86 条）**
配对等级：**A**（两侧 76 条中 41 条完全一致，含 `strh #0x1b`、`ldr w8,[x,#0x74]`、`mov w1,#0x58` 等特征序列；差异只在寄存器名与前半段）

**27.2 新增指令原文**（函数入口，紧跟 `mov x24,x0` 之后）：

```asm
fffffe000b20a55c: cbz   x1, #0xfffffe000b20a578    ; arg1 == NULL → 走"无对象"路径
fffffe000b20a560: ldrb  w25, [x1, #0x71]           ; ★ 被校验字段：arg1 + 0x71 的一个字节
fffffe000b20a564: sub   w8, w25, #3
fffffe000b20a568: cmp   w8, #2
fffffe000b20a56c: b.hs  #0xfffffe000b20a594       ; (b-3) >= 2 → 正常路径
fffffe000b20a570: mov   w0, #0x2d                  ; ★ 否则返回 45 = EOPNOTSUPP
fffffe000b20a574: b     #0xfffffe000b20a664
```

**27.0.1 同位置**（无任何取值校验，直接存储并使用该字段）：

```asm
fffffe000b1b4654: mov   x25, x1
fffffe000b1b465c: add   x26, sp, #8
...
fffffe000b1b4674: cbz   x25, #0xfffffe000b1b468c   ; 只有 NULL 检查
fffffe000b1b4678: str   x25, [x20, #0x10]
fffffe000b1b467c: ldr   w8,  [x25, #0x74]
fffffe000b1b4680: str   w8,  [x20, #0x20]
fffffe000b1b4684: ldrb  w8,  [x25, #0x71]          ; 直接采信
```

**一句话 bug 陈述**：
> 27.0.1 的 bindfs vnode 构造路径对源 vnode 的字节 `+0x71` 不做取值校验；27.2 增加「若该字节 ∈ {3,4} 则以 EOPNOTSUPP 拒绝」的门。缺该门时，类型为 3/4 的源 vnode（按 BSD `v_type` 枚举为 `VBLK`/`VCHR`，**此项为推断**）会被构造进 bindfs 对象。

**函数身份（本轮新证）**：函数内 `0xfffffe00070af0cd` 处引用字符串 **`"bindfs"`**；并在一次 5 参数调用（`w0=0, w1=0x58, x2=&栈上请求, x3=&out, w4=0`）成功后，向返回对象的 `+0x72` 写入半字 `0x1b`（若该对象是 vnode，则 `v_tag = 27`，**推断**）。

> ⚠️ 这一条同时**推翻** `CHAIN-DESIGN.md` §5 的旧命名：那处「0.988 形状匹配 → `null_getnewvnode`」是错的，实际是 **bindfs**，与 `nullfs`/`devfs`/`/dev/null` 无关。旧文档里「`/dev/null` devfs 路径无门槛可达」的整条推论失去依据。

**派发入口**：
```
0xb20a528  ← 0xb20a680（唯一直接调用者）
0xb20a680  ← {0xb20ae3c, 0xb20be24}
0xb20ae3c / 0xb20be24：__TEXT_EXEC 内直接调用者 = 0
                       其 VA 在整份 Mach-O 中以裸 8 字节指针出现次数 = 0
```
arm64e 的 vnode-op / cdevsw 表存 **PAC 签名指针**，裸指针搜索为零属预期，无法据此证伪「表派发」。
**可达性判定：不可达。** `bindfs` 需 `mount(2)` 权限；本工程身份是 uid=501 的 dev-signed app，沙箱内无 mount 权。
**危害级别**：即使可达也只是「允许把设备节点绑进 bindfs」的策略问题，**没有内存破坏形态**（该字段只被存储与同宽度读取）。

### 4.2 TCP 选项长度校验

**27.0.1 `0xfffffe000af21830`（161 条）→ 27.2 `0xfffffe000af758d8`（163 条）**
配对等级：**A**（160 条一致，仅插入 2 条，两条分支目标全部落在同一循环内）

**27.2 新增指令原文**（TCP 选项解析循环内，紧接「上一个选项处理完」之后）：

```asm
fffffe000af759e8: ldrb  w12, [x12]        ; 选项长度字节 = opt[1]
fffffe000af759ec: cmp   w12, #2
fffffe000af759f0: b.lo  done
fffffe000af759f4: cmp   w9,  w12
fffffe000af759f8: b.lt  done
fffffe000af759fc: cmp   w13, #2
fffffe000af75a00: b.ne  loop
fffffe000af75a04: cmp   w12, #4          ; ★ 新增：选项长度 >= 4
fffffe000af75a08: b.lo  loop             ; ★ 否则跳过，不做 4 字节选项解析
fffffe000af75a0c: add   x13, x10, #2     ;   然后才按 MSS/WS/SACK 读 opt[2..3]
```

**27.0.1 同位置**：`cmp w13,#2 / b.ne loop` 之后**直接** `add x13,x10,#2`，无长度下界。

**函数身份证据（逐条）**：
```asm
ldrb w8, [x5, #0xc]      ; TCP 头第 12 字节 = data offset
lsr  x8, x8, #2
and  x28, x8, #0x3c      ; doff * 4
cmp  w28, #0x15          ; 必须 >= 21
sub  w23, w28, #0x14     ; 选项区长度 = doff*4 - 20
bl   0xaefb51c           ; 把 0x28 字节头+选项拷到栈缓冲 [sp+0x10]
loop: ldrb w13,[x10]     ; 选项 kind：0=END 1=NOP 其它=TLV
add  x10, x10, w12, uxtw ; 按长度前进
subs w9,  w9,  w12
add  w11, w15, w11
sub  w11, w11, w14, lsr #16
add  w11, w11, w11, lsr #16
strh w11, [x25, #0x10]   ; 一补数校验和累加
rev16 w11, w14
strh w11, [x13]          ; 校验和回写
```
→ 判定为 **TCP 选项处理（`tcp_dooptions` 一族）**：data offset 位域、kind 0/1、40 字节拷贝缓冲、校验和回写四项同时吻合。

**一句话 bug 陈述**：
> 27.0.1 的 TCP 选项循环对长度 ∈ {2,3} 的选项不做下界过滤，会把这 2 字节当作 MSS/窗口扩大等 4 字节选项解析；27.2 补上 `cmp w12,#4; b.lo` 跳过。

**为什么不是内存破坏**：解析区是 `[sp+0x10, sp+0x38)` 的 40 字节栈拷贝，**两侧**在读取前都已存在
`cmp x13, base / cset / cmp x13, end; b.hs` 边界检查（见 27.0.1 `0xaf21960`、`0xaf21968`）。
长度 2/3 时被多读的 `opt[2..3]` 仍在缓冲内；最坏情况是 `x13 = end-1` 时的 1 字节越读/越写，**仍在本函数 0xb0 字节栈帧内**。
→ **协议正确性修复，不是可用原语。**

**派发入口**：
```
0xaf21830  ← 0xaf211b0（唯一）
0xaf211b0  ← {0xaefb8f0, 0xaf0e850}
该两支再无 __TEXT_EXEC 内直接调用者；抽查该族 4 个函数（0xaf211b0 / 0xaefb8f0 / 0xaf0e850 / 0xaf21830）均为零字符串引用（bsd/netinet 特征，非证明）
```
**可达性判定：理论可达，本轮未实测。** 本工程持有 networkextension（含 `packet-tunnel-provider`），
可经 `NEPacketTunnelProvider → utun` 向内核 IP 栈注入 TCP 段进入该解析器。
→ 属「可注入但无可利用形态」，不建议为它做设备迭代。

## 8. 最终判定

| 问题 | 答案 |
|---|---|
| 137（修正口径 159）个候选里有 app 沙箱可达的内存破坏原语吗？ | **没有找到** |
| 有几个真正的安全相关补丁？ | **2 个**（bindfs 类型门 / TCP 选项长度），均无内存破坏形态 |
| 其中可达的吗？ | bindfs 需 mount 权限 → 不可达；TCP 理论可注入但无利用形态 |
| 内核侧 S2 这一环补上了吗？ | **没有。** `CHAIN-DESIGN.md` 的缺口不变 |

**总评**：`com.apple.kernel` 的 dChk>0 集合里，约 60% 是功能新增与状态机扩宽（bindfs、IPv6 策略、新消息类型），约 25% 是防御性加固（NULL/全局/溢出），其余是方法假象。**这个分布与「27.2 是功能性大版本、不是安全版本」一致**，也与 `STATUS.md` §C「iOS 27.0.1 / 27.1 公告无任何 CVE」吻合。

→ **建议把 `com.apple.kernel` 从候选池移出**，不再在 dChk 排名上投入设备迭代。若还要在内核侧找 S2，应换靶：优先选**有 UserClient 且有 external method 的 kext**（可达性可静态证明），而不是无符号的 `com.apple.kernel`。

## 9. 方法学记录（本轮踩到的坑）

1. **「137」不是事实，是三个方法选择的产物。** 位置配对→129，边界规则→159。任何引用此数字的文档都要标口径。
2. **边界规则必须自证。** 自证办法：统计「被判为函数体内、却以 `pacibsp` 开头」的位置，看其后一条是否为栈帧建立指令。6807/6807 命中 → 规则错。此法可推广到任何 kext。
3. **dChk 不足以防重排。** 必须配「校验签名多重集」：只重排不增语义时 dChk>0 而净签名=0（159 个里 15 个属此）。
4. **共享插入序列检测很便宜**：插入指令序列去掉 `adrp/b/ret` 后哈希，即可看出「同一段代码被复制到 N 个函数」。本轮只发现 4 组、最多 4 成员 —— 说明我先前「大部分是同一内联模板」的直觉**是错的**，靠数据纠正了。
5. **哈希/位域运算长得像边界校验**（§2.3）。判别：出现「乘法常数 + 移位异或 + 与表容量掩码」三者同时存在，就不要当边界检查。
6. **字符串锚点是最便宜的函数身份来源。** 一个 `adrp/add` 解析出 `"bindfs"` 就把悬了多轮的候选定性了。建议对所有 kext 预建 `adrp/add → __cstring` 表。
7. **PAC 让「引用计数」失效。** 表派发函数查不到裸指针，别把「0 引用」当「死代码」。
8. **不要替未复核对数下结论。** 本轮 37 个「未定性」宁可留白，也不按「看起来像状态比较」批量标成功能新增——这个工程已因批量推断误判过五次。
