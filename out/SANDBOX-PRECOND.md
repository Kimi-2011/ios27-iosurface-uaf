# `com.apple.security.sandbox` `0xa8eee60` 前置条件：四问四答

工具：`tools/xref_views.py`（新增；逐函数反汇编，不用线性扫）
对象：27.0.1 `0xfffffe000a8eee60` → 27.2 `0xfffffe000a93d1d0`

**一句话结论：这不是用户可控授权标志的缺失，是「签名加了一个上下文参数 + 状态一致性收紧」。
行为差异真实存在，但 `x1` 来自内部对象，不是用户态数据。倾向于逻辑重构，不是沙箱策略绕过。**

## 1. `bl` 调用者：只有 2 个

| 版本 | 目标 | `bl` 调用者 | `adrp+add` 取地址 | 数据段指针槽 |
|---|---|---|---|---|
| 27.0.1 | `0xa8eee60` | **2** | **0** | **0** |
| 27.2 | `0xa93d1d0` | （同构，见 §2） | 0 | 0 |

```
调用点 0xa8eee38   在函数 0xa8eee14（76 B）
调用点 0xa8ef08c   在函数 0xa8eefa0（260 B）
```

零取地址、零数据槽 ⇒ **不是回调表里的函数指针**，只有这两条直接调用路径。

## 2. 每个调用点 `x1` 是什么（这是核心）

### 27.0.1：两个调用点都**没有设置 x1**

```
0xa8eee14 (wrapper1):
  +0x14  mov  x19, x0
  +0x18  bl   0xa8eea3c        ; x0 = getter(this)
  +0x1c  mov  x20, x0
  +0x20  mov  x0, x19          ; x0 = this
  +0x24  bl   0xa8eee60        ; ★ x1 从未被赋值
```

`x1` 沿用进入函数时的值 —— 而 `bl 0xa8eea3c` 按 ABI 会破坏 `x1`。
**⇒ 27.0.1 的目标函数压根不读 `x1`**（它读的是 `x19+0xa8`），所以这里"没设"是自洽的。

### 27.2：两个调用点都新增了 `mov x1,x20`

| 27.0.1 | 27.2 | 变化 | `x20` 是什么 |
|---|---|---|---|
| `0xa8eee14`（76 B） | `0xa93d180`（80 B） | **+1/−0 = `mov x1,x20`** | `bl 0xa8eea3c(this)` 的返回值 —— **getter/查表得到的对象** |
| `0xa8eefa0`（260 B） | `0xa93d31c`（264 B） | **+`mov x1,x20`**（另有 `ldrh [x21,#0x7f8]`→`[x21,#0x160]` 布局位移） | `bl 0xa904f44(...)` 返回后 `mov x20,x0` —— **新建的对象** |

**⇒ 函数签名变了：`f(this)` → `f(this, ctx)`。** 两个调用者都被要求显式传 `ctx`。

## 3. `arg1->0xc` 是什么字段

同族函数 `0xa8eec64`（也调 `0xa8eea3c` 拿同一个对象）把布局读出来了：

```
0xa8eec64:
  bl   0xa8eea3c
  mov  x20, x0
  ldrb w8, [x0, #0xc]        ; ← 和 27.2 目标函数检查的是同一个字节
  tbz  w8, #0, ...           ; ← 同一个 bit0
  ldrb w8, [x20, #0xd]
  mov  w9, #2
  bfxil w9, w8, #0, #1       ; w9 = 2 | (ctx+0xd 的 bit0)
  ldr  w8, [x20, #8]
  cmp  w8, w9                ; ★ 把 +8 的 u32 状态和 {2|bit} 比
  b.ne ...
```

**对象布局（实测）**：

| 偏移 | 类型 | 含义 |
|---|---|---|
| `+0x8` | u32 | **状态值**，被拿去和 `2 \| (bit)` 比较 |
| `+0xc` | u8 | **flags，bit0 = 目标函数检查的那一位** |
| `+0xd` | u8 | 另一位标志（bit0 参与状态计算） |
| `+0x10` | 指针 | wrapper2 里 `ldr x9,[x8,#0x10]! ; blraa x9,x8` 走虚方法 |

**⇒ 这是一个小状态对象：`+8` 状态机值、`+0xc/+0xd` 两个标志字节。**
`+0xc` bit0 不是"权限"，更像"某种模式/阶段已设置"。

## 4. 从用户态怎么到达

| 入口 | `bl` 调用者 | `adrp+add` | 数据槽 |
|---|---|---|---|
| wrapper1 `0xa8eee14` | **0** | **0** | **0** |
| wrapper2 `0xa8eefa0` | 2：`0xa8fabb4`（在 `0xa8fa7f4` 内）、`0xa900c8c`（在 `0xa900910` 内） | 0 | 0 |

**wrapper1 零引用的形态和你说的 IOSurface 那三个函数一模一样** —— 大概率是 KPI 导出，
经启动时填充的 GOT 槽被别的 kext 调用，静态看不见。**这不等于死代码。**

wrapper2 往上还有两层（`0xa8fa7f4` 本身是 1008 B，在沙箱的改动函数名单里）。

## 5. 邀你判断：是漏洞还是重构

### 支持「重构」的证据（我认为占多数）

1. **签名加参**：两个调用点各加一条 `mov x1,x20`，目标函数入口改读 `x1+0xc`。
   编译器为签名变化重排是很自然的。
2. **旧检查没消失**：`this->0xa8` 从入口搬到 `+0x13c` 退出路径（极性 `cbnz`→`cbz` 反转）。
   如果目的只是"加一道门"，没必要把旧判断挪位置。
3. **`x1` 不是用户数据**：wrapper1 里来自 getter/查表，wrapper2 里是新建对象。
   **没有一条路径把用户态缓冲区喂进 `x1`。**

### 支持「安全修复」的证据（必须记下来）

**27.0.1 在 `ctx->flags.bit0 == 0` 的情况下仍然进入主流程，27.2 不进。**
主流程第一件事是 `ldr x0,[x19] ; bl <X>`，然后按 `this->0x46` 计数遍历 `this->0x60` 数组逐个 `bl`。
**那件"多做的事"具体是什么，需要在函数体内精读一遍才算定论。我没有读到底，这里不下结论。**

### 一个我没解掉、也没法硬下的点

27.2 的 `+0x140  cbz x8, +0x38` 目标 `+0x38` 在 `ldar w9,[x8]` **之后**。
若 `ctx->flags.bit0 == 0` **且** `this->0xa8 == 0` **且** `w9 == 0`，三级条件同时成立时看起来会回到 `+0x38`
再走到 `+0x3c`（`ldrb/tbz`）形成回路。
**但这需要实战路径才成立，我没有证据说它是死循环 —— 只标注"静态可疑，未验证"。**
