## 0. 撤回：我把 `bic` 的方向读反了

`out/KERNEL-CHECKS.md` §3 我写的是「只允许 `w1` 取 `0xC0` 的子集」「`w1 & 0x600` 恒为 0 ⇒ 那段抽 bit9/bit10 的代码变死代码」。

**这两条都错了。撤回。**

`BIC Wd, Wn, Wm` = `Wd = Wn AND NOT Wm`：

```asm
mov  w9, #0xc0
bic  w9, w9, w1        ; w9 = 0xC0 & ~w1
cbnz w9, body          ; 非零 → 拒绝
```

非零 ⇔ `0xC0` 里存在某一位不在 `w1` 中 ⇔ **`w1` 必须同时置位 bit6 和 bit7（0xC0 ⊆ w1）**。
其余位**不受约束** —— 包括 bit8、bit9、bit10。

**⇒ 正确的说法：27.2 要求 `w1` 至少含 `0xC0` 这两位。不是「只允许两位」。**

**连带撤回**：`w1 & 0x600` 没有被强制为 0，所以 `+0x60` 那段抽 bit9/bit10 的代码 **27.2 里依然是活的**。
「加了校验后变死代码」这个推论不成立，删掉。

**S 级判定不受影响**（真新增、27.0.1 无等价判断、被拦路径有具体动作），但**依据从「越权位被挡」改成「必备位没检查」**：

> 27.0.1 允许 `w1` 不含 `0xC0` 就进函数体；27.2 拒绝。

只要 `w1` 的 bit6/bit7 是「调用方能力/模式已就绪」一类标志，27.0.1 就是在**未就绪状态下继续执行**。
方向变了，性质还是「缺前置条件检查」。

## 1. Q1：`x0` 是什么对象

全函数（596 B）读到的字段：

| 偏移 | 宽度 | 用途 | 证据 |
|---|---|---|---|
| `+0x00` | 指针 | **vtable**（PAC 签名，`autda` + `blraa`，槽 `0x88`） | `+0xe4 ldr x16,[x0]` / `+0xf4 ldr x8,[x16,#0x88]!` / `+0x108 blraa x8,x16` |
| `+0x20` | u32 | **状态/标志字**：`&0xf0 == 0x20`、`bit18`、`&0xb0 == 0x10` | `+0x18` / `+0x38 tbnz w20,#0x12` / `+0xb4` |
| `+0x22` | u8 | 标志位，**bit5** | `+0xd8 ldrb w8,[x0,#0x22]` / `+0xdc tbz w8,#5` |
| `+0x50` | 指针 | 传给 vtable 槽 `0x88` 的第 3 个参数 | `+0xe0 ldr x3,[x0,#0x50]` |
| `+0x88` | u32 | **计数器**，读-加-写（`ldr/add/str`，在锁内） | `+0xc8 ldr w8,[x0,#0x88]` / `+0xd0 str w9,[x0,#0x88]` |
| `+0xa8` | 指针 | 指向 `{+0x8: 锁字}` | `+0x3c ldr x8,[x0,#0xa8]` / `+0x50 add x13,x8,#8` |

**锁**：

```asm
+0x48  mrs   x9, tpidr_el1        ; per-CPU 基址
+0x4c  ldr   w12, [x9, #0x4f8]    ; 取本 CPU 号
+0x50  add   x13, x8, #8
+0x54  casa  x11, x12, [x13]      ; x11=0；若 [x8+8]==0 则置为 cpu号
+0x58  cmp   x11, #0
+0x5c  b.ne  +0x88                ; 已被占用 → 走阻塞路径
```

⇒ **`[[x0+0xa8]+8]` 是「0 表示未占用」的自旋/自适应锁字，`casa` 是无人竞争时的加锁。**
`+0x88` 的计数器在锁内自增 —— 典型的**引用计数 / 使用计数**。

### 结论：这不是 `proc` / `task` / `kauth_cred` / `socket`

判据是 **`+0x00` 是 PAC 签名的 vtable 并且被 `autda`+`blraa` 调用**。
BSD 侧那几个结构体没有 vtable；这是 **C++ 对象（libkern/IOKit 基类那一族）**。

**⇒ 优先级按你的标准要降一档**：不是凭证/进程结构体，是内核 C++ 对象。
但它的 `+0x20` 是个**多功能标志字**（至少 3 组独立位域在用），`+0x88` 是用计数，
`w1` 是调用方传进来的**能力/模式字** —— 「标志位 + 引用计数 + 跨边界传参」的组合仍然值得跟。

## 2. Q2：`w1` 从哪来 —— **追不到，且原因很硬**

### 我做了什么（先验方法）

按你的规矩，零命中先用已知正例验：

| 目标 | 说明 | 命中 |
|---|---|---|
| `0xb347e20` | 已知正例（本函数 `+0x70` 调用它） | **2 处** —— `0xb347a78`（外部）+ **`0xb3484c0`（就是本函数的 `+0x70`）** |
| `0xb348450` | 待查目标 | **0 处** |

**方法有效**（正例命中，且命中的正是我预期的那一处调用点）。

### 然后扫全部 21731 个函数，四种直接分支形态

`b` / `bl` / `blr` / `braa` / `blraa` / `blraaz` 里目标是 `0xb348450` 的：**0 处**。
另有 `adrp+add` 取地址 **0 处**、数据段指针槽 **0 处**。

### 但这次不能推「死代码 / 不可达」

两个理由，都是我这一支自己踩过的坑：

1. **chained fixups 里 59% 是 BIND** —— 跨 kext 调用在静态镜像里根本不表现为地址（你上一轮更正的）。
2. **`com.apple.kernel` 是 KPI 提供方** —— 它在 `__LINKINFO` 里导出 6168 个符号名（`out/LINKINFO-NOTES.md`），
   而那份表**只有名、没有地址**。被别的 kext 通过 BIND 调用的函数，在本镜像内必然 0 命中。

**⇒ `w1` 的来源在镜像之外。Q2 静态答不出来，写「未定」。**

要答它只有两条路，都不便宜：
- 解 `LC_DYLD_CHAINED_FIXUPS` 的 imports 表（ordinal → 符号名），再反查哪个 kext 导入了它 —— **你已推迟**
- 用 `__LINKINFO` 的 6168 个名字反推（无地址，只能靠**函数体特征匹配**已知实现）

### 一个能说的旁证

**函数体以 `bti c` 开头**（27.2 侧 `0xb39e868` 第一条就是 `bti c`）。
`bti c` 只对**间接分支**有意义 ⇒ **这个函数确实是通过函数指针/表项被调用的**，
不是被直接 `bl` 调用的。这和行为是 0 个直接调用者**互相印证**，而不是矛盾。

## 3. 顺带确认了一件事：`w1` 的 bit8 在本族里被用

下游 `0xb347e20` 里读 `w1` 的两个位：

```asm
+0x20  mov   x20, x1
+0x8c  tbz   w20, #0, +0xc4        ; bit0
...
+0x124 tbnz  w1, #8, ...           ; bit8（在 27.0.1 路径里）
```

而第 1、2 条修复正好是**清 `[(x0+0x18)+8]` 的 bit8**。
两处都落在 bit8 上，**目前只是巧合还是同一条线，我判不了**，记在这里备查。
**不要当成结论** —— 一个是 `x0+0x18` 指向对象的 `+8`，一个是 `w1` 寄存器的 bit8，不是同一个字段。

## 4. 汇总

| 项 | 结果 |
|---|---|
| Q1 `x0` 是什么 | **内核 C++ 对象**（`+0x00` PAC vtable），字段表见 §1；**不是** proc/task/kauth_cred/socket |
| Q1 优先级 | 降一档：不是凭证结构体，但含多功能标志字 + 引用计数 + 跨边界传参 |
| Q2 `w1` 来源 | **未定**。全镜像 0 直接调用者（四种分支形态 + 取地址 + 数据槽），方法已用正例验证 |
| Q2 能确定的 | 0 调用者 + `bti c` 开头 ⇒ **只经间接分支调用，调用方在本镜像之外（KPI/BIND）** |
