# AppleAVD 27.0.1：拷贝路径缺少容量检查（越界写候选）

**日期**：2026-11-01 00:40
**目标**：`com.apple.driver.AppleAVD`（视频解码，VideoToolbox 可达）
**对应公告**：27.2 Kernel **OOB write CVE-2026-112416 / CVE-2026-112415**
**方法**：`BTI` 起点 + 指令归一化差分（该差分器已用 `kdiff.py` 的 108 交叉验证）

## 一、改动范围极小

AppleAVD 两版之间**只有 6 个函数改动**：

| Δ指令 | 27.0.1 VA | 27.2 VA | 指令数 |
|---|---|---|---|
| **+22** | `0xfffffe0008707cf0` | `0xfffffe000873e2e0` | 272 → 294 |
| +1 | `0xfffffe0008710cd4` | `0xfffffe00087472c8` | 80 → 81 |
| 0 | `0xfffffe000870d2e0` | `0xfffffe00087438d4` | 136 → 136 |
| 0 | `0xfffffe000870b44c` | `0xfffffe0008741a40` | 627 → 627 |
| 0 | `0xfffffe00086c4084` | `0xfffffe00086fa674` | 128 → 128 |
| **−21** | `0xfffffe0008708130` | `0xfffffe000873e778` | 35 → 14 |

## 二、核心：27.2 新增了完整边界检查

### 27.2（`0xfffffe000873e2e0` 内新增块）
```asm
ldr   x9,  [x11]            ; x9 = 缓冲区描述符
str   xzr, [x11]            ; 清空（防重入/防 UAF）
ldr   w10, [x27, #I]
cbnz  w10, skip
ldr   w10, [x26, #I]
cbnz  w10, skip
cbz   x9,  skip             ; 描述符为空则跳过
adds  w10, w8, w24          ; w10 = 偏移 + 长度
b.hs  fail                  ; ★ 无符号溢出 → 拒绝
ldr   w11, [x9, #I]         ; w11 = 容量字段
cmp   w10, w11
b.hi  fail                  ; ★★ 超出容量 → 拒绝
ldr   x9,  [x9, #I]         ; x9 = 缓冲区基址
cmp   w24, #I
csel  w1,  w24, w10, lo     ; ★ 拷贝长度截断到 min(len, 剩余)
add   x0,  x9, x8           ; 目标 = 基址 + 偏移
bl    #I                    ; → 拷贝
```

### 27.0.1（同位置）
```asm
ldr   w8, [x27, #I]
cbz   w8, ...
mov   x0, x20
mov   x2, w24               ; ← 长度直接作为第三个参数透传
mov   x3, x21
bl    #I                    ; → 拷贝，无任何容量/溢出检查
```

**结论（反汇编直接可见）**：27.0.1 **不做** `偏移+长度 <= 容量` 校验，
也**不做** `偏移+长度` 的溢出检测。这正是「越界写」的充分形态。

## 三、待确认的两点

### 3.1 `w24` 是否来自码流
`ldr w24, [x27, #I]` —— `w24` 是结构体字段。
**需要确认**：这个结构体是 AVD 从**码流**解析出来的（如 SPS/PPS 或 DPB 尺寸），
还是由固件/内核侧填入。
- 若来自码流 → **攻击者可控**，可直接打成越界写
- 若来自固件 → 只能在本地文件/受信路径触发

*这一点的判定方法与 AVE 那次的教训一致：不能只看"像参数"，要确认真实数据流。*

### 3.2 可达性
AppleAVD 经 **VideoToolbox 解码**（`VTDecompressionSession`）驱动，
在本工程中**已实测 app 可驱动 AVE 编码**（同一 VideoToolbox 框架），
AVD 走对称路径，预期可达。但**尚未在 AVD 上实测**。

## 四、与 Skywalk / AVE 的对比

| 目标 | 改动函数 | 数据流是否清楚 | 可达性 |
|---|---|---|---|
| **AppleAVD** | **6** | 清楚（有容量字段、有截断逻辑） | VideoToolbox，预期可达 |
| IOSkywalkFamily | 108 | 清楚（尺寸下界 + 清存活位） | ✗ 无 UserClient，上游 Wi-Fi kext 不在本缓存 |
| AppleAVE2 | — | **不清楚**（读取点全是日志形态） | 已实测可达 |
| AppleH16ANE | 155 | 不清楚（像新增数据结构） | CoreML 可达 |

**AppleAVD 目前是性价比最高的内核目标**：改动最小、语义最清楚、可达路径已知。

## 五、下一步（按优先级）

1. **确认 `w24` 的数据来源**——追 `x27` 结构体的写入点，看是否有码流解析路径
2. 用 `VTDecompressionSession` 在真机上构造畸形码流触发该拷贝路径（打日志确认进入）
3. 若 `w24` 可控，构造 `w24 > capacity - offset` 的输入，观察是否崩溃（`EXC_BAD_ACCESS` 内核态）
4. 同时检查 `−21` 条的那个函数（`0xfffffe0008708130`）——代码被删同样可能是修复

## 六、`−21` 条函数的补充证据（00:45）

`0xfffffe0008708130`（35 条）→ `0xfffffe000873e778`（14 条）。

### 27.0.1 原文
```asm
bti   c
mov   w8, #I
add   x8, x0, x8
ldr   w8, [x8]
and   w8, w8, #I
cmp   w8, #I
b.ne  ...                    ; 标志不符 → 另一分支
add   x8, x0, #I
; ── 取模 + 钳制序列（除以常数 / ubfiz / cmp / csel）──
ldr   x8, [x10]
str   xzr, [x10]             ; 清描述符
cbz   x8, ...
adds  w9, w1, w2             ; 长度相加
b.hs  ...                    ; 溢出检查
ldr   w10, [x8, #I]          ; 容量
cmp   w9, w10
b.ls  ...                    ; 容量内 → 继续
ret
ldr   x8, [x8, #I]
add   x0, x8, w1, uxtw       ; ★ 目标地址 = 基址 + w1，此前仅 cmp w2,#I
cmp   w2, #I
```

### 27.2 原文（整段替换为直接校验）
```asm
bti   c
cbz   x1, ...
adds  w8, w2, w3
b.hs  ...
ldr   w9, [x1, #I]
cmp   w8, w9
b.ls  ...
ret
```

**解读**：27.0.1 把「取模+钳制+描述符清零+容量检查」这一整套**内联**在函数里，
且末尾 `add x0, x8, w1, uxtw` 之后只有 `cmp w2, #I`（单值上界），
**缺少 `w1 + w2 <= capacity` 的组合校验**。
27.2 删掉内联版本，改为调用共享的、带完整检查的辅助函数。

两个函数的改动**从不同角度指向同一结论**：
27.0.1 的 AVD 拷贝路径缺少「偏移+长度 ≤ 容量」校验与溢出检测。

## 七、已知局限（不要重复 AVE 的错误）

- 上面的结论**限于反汇编层面**：27.0.1 确实没有这些检查指令
- **尚未证明** `w24` / `w1` / `w2` 来自码流。这是能否成为真漏洞的关键
- 尚未在真机上实测触发

在确认数据来源之前，**不要对外称之为"可用的越界写"**，只能称"缺少校验的拷贝路径"。

## 八、追 `w24` 数据源（01:00）：进展与一个假阳性

### 8.1 精确链条

```asm
; 27.0.1  0x8707cf0
and  w24, w1, #0xf          ; 索引 = 参数1 低4位 → 0..15
ldr  x8,  [x0, #0x140]      ; x8 = 记录数组基址
mov  w9,  #0xe58
umull x9, w24, w9           ; 步长 0xE58
add  x27, x8, x9            ; x27 = 记录[idx]

ldr  w1,  [x27, #0xd80]     ; 偏移字段
ldr  w24, [x27, #0xd84]     ; ★ 拷贝长度
ldr  w8,  [x27, #0xe30]     ; 标志
cbz  w8, ...
mov  x0,  x20               ; this
mov  x2,  w24               ; 长度
mov  x3,  x21               ; 参数1
bl   0xfffffe0008708130     ; ← 正是 27.2 中被砍掉 21 条的同一函数
```

调用目标与「−21 条」那个函数**是同一个**，两条线索合流了。

### 8.2 记录数组的来源

同区域内 `0x86d42fc` 是对象初始化器：
```asm
cmp  w19, #0
mov  w8, #0x1080000
csel w8, w8, w19, eq
dup  v0.4s, w8
add  v1.4s, v0.4s, v1.4s      ; base + 常量偏移
stp  q1, q2, [x0, #0x140]     ; ★ 写入 this+0x140（记录数组基址）
stp  q1, q2, [x0, #0x160]
...
```
→ 记录数组在**对象初始化时用静态常量铺开**，基址存于 `this+0x140`。

### 8.3 一个必须记下的假阳性

我一开始用「扫描立即数 `#0xd84`」找写入点，命中 `0x86d42b4`。
实际那处是：
```asm
adrp x8, #0xfffffe00071a2000
add  x8, x8, #0xd84      ; ← __cstring 内的字符串偏移
str  x8, [sp]
bl   #0xfffffe000871d604 ; ← 日志函数
```
**是字符串地址，不是结构体字段。**
→ 「立即数相等」不能用来定位字段写入点（字符串偏移、其它常量都会混入）。
定位 `record+0xD84` 的写入者**必须做数据流分析**，不能靠立即数匹配。

### 8.4 当前结论

- ✅ 已确认：长度来自 16 槽 × 0xE58 记录数组中某条记录的 +0xD84 字段
- ✅ 已确认：记录数组基址在 `this+0x140`，由初始化器写入
- ❓ **未确认**：该字段是否可被用户态写入（会话配置 / 码流参数）
- ❓ 未确认：`arg1 & 0xF` 的索引是否由用户控制

**在解决 ❓ 之前，AVD 仍是「缺少校验的拷贝路径」，不是「已确认的越界写」。**

### 8.5 下一步的正确方法

不要再用立即数扫描。改为：
1. 在 `__TEXT_EXEC` 中找所有以 `0xE58` 为步长计算地址的代码（`umull`/`madd` with `#0xe58`），
   这些才是真正访问该数组的位置
2. 从这些位置中筛出**写**（`str`）而不只是读
3. 逐一确认写入的值来自参数/码流还是常量

## 九、附带发现：0xE58 步长地址被送进解码固件命令字（01:15）

按 8.5 的方法扫描「以 0xE58 为步长计算地址」的代码后，发现其中 4 处
（`0x86ebfc8` / `0x86ec208` / `0x86ec438` / `0x86ec520`）不是普通访存，而是**构造固件命令字**：

```asm
ldrh w10, [x12, #6]         ; 16 位索引
mov  w11, #0xe58
mul  w11, w10, w11          ; idx * 0xE58   —— 无钳制、无上界检查
add  w10, w11, w9
and  w12, w10, #0x3fffc     ; 18 位地址掩码
mov  w13, #1
movk w13, #0x158, lsl #16
orr  w12, w12, w13          ; 拼命令位
add  w12, w12, #0xc40, lsl #12
str  w12, [x8]              ; → 命令寄存器，交给解码固件
```

含义：内核把 `基址 + idx*0xE58` 算成 32 位命令字发给**视频解码固件**，
地址被截到 18 位。若 `idx` 超范围，固件会访问记录数组之外的内存。

**但注意**：这 4 处在 27.2 中**未被修改**（改动函数只有 6 个，不含它们），
所以**不是本次公告的修复对象**。记录在此备用，不作为当前线索。

## 十、AVD 线索最终状态（诚实的收尾）

### 已确立
| 事实 | 证据 |
|---|---|
| AppleAVD 两版仅 6 个函数改动 | 归一化差分 |
| 27.2 在拷贝路径新增 `adds/b.hs` 溢出检测 + `cmp capacity/b.hi` + `csel` 截断 | 逐条反汇编 |
| 27.0.1 同位置直接 `mov x2, w24` 传长度，无检查 | 逐条反汇编 |
| 拷贝长度 = 16 槽 × 0xE58 记录数组的 `+0xD84` 字段 | `ldr w24,[x27,#0xd84]` |
| 数组索引 = 参数1 低 4 位（0..15） | `and w24, w1, #0xf` |
| 数组基址在 `this+0x140`，由初始化器写入 | `stp q1,q2,[x0,#0x140]` |
| 0xE58 步长地址也被编成固件命令字 | 4 处命令构造 |

### 未确立（关键缺口）
- ❓ `record+0xD84` 是否可被用户态写入
- ❓ 参数1（决定索引）是否来自用户输入
- ❓ 该路径是否能在真机上被 VideoToolbox 触发

**因此 AVD 的定性是：27.0.1 确实存在一条缺少容量校验的拷贝路径，
但它是否构成可用的越界写，取决于上述三个未决问题。**

### 方法论记录
1. 「立即数相等」不能定位字段写入点 —— 字符串偏移会混入（8.3 已踩）
2. 应改用「步长计算点」定位数组访问者（9 节的做法，有效）
3. 本工程已经反复因**未验证前置条件**而误判（AVE 的 0x1888、323478 的 GC），
   这里必须先解决 ❓ 再下结论

## 十一、记录数组是内核分配的页对齐缓冲区（02:20）

### 11.1 分配点

`0x87087dc`（仅 27.0.1 存在，27.2 已无此常量）：
```asm
str  x0, [x19, #0x6018]
cbz  x0, fail
add  x1, x21, #0x10
add  x2, x19, #0x148        ; ★ 描述符落在 this+0x148
mov  x0, x19
mov  w3, #0xe580            ; ★ 16 × 0xE58
bl   #0xfffffe0008708ce8
cbz  w0, fail
```

### 11.2 分配函数 `0x8708ce8` 的行为
```asm
ldr  x24, [x24, #0xc90]     ; 页大小/对齐全局
ldr  x8,  [x24]
neg  x9,  x8
add  x10, x8, w3, uxtw      ; align + size
sub  x10, x10, #1
and  x10, x10, x9           ; round_up(size, align)
lsr  x10, x10, #0x20        ; 超 4GB → 走错误日志
```
标准**页对齐分配 + 溢出检查**。

### 11.3 结构关系
```
this+0x140 : 记录数组基址指针（ldr x8,[x0,#0x140]）
this+0x148 : 分配描述符（ldrb w8,[x19,#0x148]; tbz w8,#0 → 已分配标志）
数组实体   : 0xE580 字节 = 16 条 × 0xE58 记录
记录布局   : +0xD80 偏移, +0xD84 长度（★越界写候选）, +0xE30/+0xE34 标志
```

### 11.4 为什么强烈怀疑该缓冲区与解码固件共享

同一 `base + idx*0xE58` 计算在 4 处（`0x86ebfc8` / `0x86ec208` /
`0x86ec438` / `0x86ec520`）被编成 **32 位固件命令字**：

```asm
ldrh w10, [x12, #6]
mul  w11, w10, #0xe58
add  w10, w11, w9
and  w12, w10, #0x3fffc     ; 18 位地址
orr  w12, w12, #0x1580000
str  w12, [x8]              ; → 命令寄存器
```

→ 这块缓冲区是**内核与视频解码固件共同寻址的**。
若 `record+0xD84` 由固件在解析码流后写入，则该长度对**攻击者可控的码流**敏感。

### 11.5 由此形成的完整假设链

```
攻击者提供的视频码流
   → 解码固件解析（固件不做/少做长度检查）
   → 固件把尺寸写入共享记录的 +0xD84
   → 内核 27.0.1 直接以该长度拷贝（无容量校验、无溢出检测）
   → 越界写（内核态）
```

这与 Apple 公告把 AppleAVD 的 OOB write 列为**内核漏洞**是自洽的：
内核信任了固件写入的尺寸字段。

### 11.6 仍未证实（必须诚实标注）

- ❓ **没有直接看到固件写 `+0xD84`**。「固件写入」是【推断】，
  依据是「该缓冲区同时被固件命令字寻址」+「内核侧无写入该字段的指令」
- ❓ 该缓冲区是否映射为 DMA／共享内存尚未确认
- ❓ 未在真机上触发

**结论等级：假设链完整且自洽，但缺最后一环的直接证据（固件写入点）。**
这一环无法纯静态确认——需要真机在编解码时 dump 该缓冲区内容。

## 十二、修正（02:40）：记录结构在 27.2 缩小了，跨版本偏移不可比

### 12.1 实测

| | 步长 | 分配尺寸 | 记录数 |
|---|---|---|---|
| 27.0.1 | `mov w9, #0xe58`（`0x8707d48`） | `mov w3, #0xe580`（`0x87087dc`） | 16 |
| 27.2 | `mov w9, #0xe50`（`0x873e338`） | `mov w3, #0xe500`（`0x873edd0`） | 16 |

**记录体缩小了 8 字节**（0xE58 → 0xE50）。

### 12.2 后果
`+0xD84` 在 27.2 中落在**不同的逻辑字段位置**上（结构变小 → 后续字段前移）。
因此：
- ❌ 不能说「27.2 给 0xD84 字段加了检查」
- ✅ 只能说「27.2 在这个拷贝路径上加了一套容量校验」

后者才是证据链要的东西，后者成立。

### 12.3 为什么结论仍然成立

判断依据是 **27.2 在同一调用位置内联了 `adds/b.hs` + `cmp capacity/b.hi` + `csel` 截断**，
而 27.0.1 在同一位置是 `mov x2, w24` 直接透传长度 + `bl`。
这是**结构性差异**，不依赖跨版本偏移相等。

### 12.4 这是第四次同类教训
| # | 错误 | 根因 |
|---|---|---|
| 1 | AVE 0x1888 当索引 | 未追数据流 |
| 2 | AVD 0xD84 当字段 | 立即数匹配不可靠 |
| 3 | skywalk 内联当校验 | 口径错，应看 dChk |
| 4 | AVD 跨版本比偏移 | **结构体大小变化导致偏移漂移** |

→ 新增铁律第 5 条：**跨版本比较任何字段偏移前，必须先确认两侧结构体步长/尺寸一致。**

## 十三、追到源头（2026-11-01 09:50）：索引来自硬件寄存器，不是用户参数

### 13.1 完整数据流（逐跳反汇编确认）

```
① 0x86df484  函数入口
   cmp w1, #1 ; b.hi fail        ← 参数1 本身被限制 ≤1

② 0x86df4e0  sub x22, x29, #0xd0  ; 栈结构
   0x86df4f4  stur q0, [x29, #-0xc0]   ; 清零 -0xc0..-0xb0

③ 0x86df59c  sub x1, x29, #0xc0
   0x86df5a0  bl 0x86d8014             ; ★ 填充该结构

④ 0x86d8014
   ldr w1, [x10]                       ; 来自对象字段
   mov x2, x20                         ; &结构
   mov w3, #0x14                       ; 20 次
   bl  0x86d8114

⑤ 0x86d8114（真正的数据来源）
   ldr  x22, [x0, #0x6d0]              ; 硬件接口对象
   loop:
     ldr   x16, [x22]
     autda x16, x23
     ldr   x8,  [x16, #0x18]!
     blraa x8,  x16                    ; ★ PAC 签名虚调用 → 读硬件寄存器
     str   w0,  [x20], #4              ; 存入结构
     subs  w19, w19, #1
     b.ne  loop

⑥ 回到 0x86df484
   ldur w9, [x29, #-0xbc]              ; = 结构的第 2 个字段 = 硬件寄存器值
   stp  w9, w8, [sp, #0x80]
   ...  → 作为 w1 传给 0x8707c34
   → w1 & 0xF  →  记录数组索引
```

### 13.2 结论

**记录数组索引 = 视频解码硬件寄存器的值 `& 0xF`**，
**拷贝长度 = 该记录在 +0xD84 的字段**，两者都源自
**硬件/固件侧**，不是经系统调用或 IOKit 参数直接传入的用户整数。

### 13.3 对可利用性的判定

| 问题 | 结论 |
|---|---|
| 能否用普通参数构造越界？ | **不能**。索引来自硬件寄存器，长度来自共享记录 |
| 攻击者能否间接影响？ | 只能通过**码流**影响固件行为（【推断】，未证实） |
| 是否简单原语？ | **不是** |

**→ AVD 这条从「候选漏洞」降级为「纵深防御层面已修复的代码缺陷」。**
27.0.1 确实缺校验，但触发它需要先让固件产生异常尺寸，
这已超出「从 app 沙箱直接打」的范畴。

### 13.4 这一结论的价值

它关掉了一条**看起来最像漏洞的线索**，且是走完完整数据流才关掉的——
不是靠猜测。这避免了把「加个检查」误当成「可打的漏洞」而浪费后续设备迭代。
