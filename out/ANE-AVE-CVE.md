# ANE-AVE-CVE — 按 27.2 公告的修复措辞做定向差分

1. **依据**：`out/advisory-27.2.json`（iOS 27.2 安全性内容，本地存档）。这些是 **27.2 才修**的 ⇒ 27.0.1 上全部存在。
2. **先验变了**：公告给了修复**方式**（bounds checking / input validation / locking），这比 dChk 增量强得多 —— dChk 只能指出「哪里变了」，公告指出「变的是什么」。
3. **本轮撤回**：① ANE 42 个 dChk>0 判为「防御性加固」→ **撤回**，公告证明其中含真实 OOB write 修复；② AVE「要 proreshw entitlement，先出局」→ **须重核**，公告把 AVEVideoEncoder 单列为组件。
4. **另撤回**：IOSurface 那条是**竞态 / improved locking**（CVE-2026-112477），而 §1 审的是长度/索引属性路径 —— **找错了缺陷类别**，§1 的"未发现越界"不覆盖这条 CVE。
5. **本轮实际做了什么**：定义新指标「受保护的寄存器索引访问」（guard-before-indexed-access），对 `ane.27.0.1.macho` vs `ane.27.2.macho` 全量跑差分。
6. **结果**：A=4284 函数、B=4409 函数、改动对 158；指标总数 348 → 358；**只有 2 个函数指标上升**。
7. **关键**：这 2 个候选**逐条手读后全部是配对假象**（详见 §4），不是真差分。所以本轮**没能定位到任何一条 CVE 的修复点**。
8. **卡点**：无符号（`nsyms=0`）⇒ 跨版本函数配对只能靠内容对齐；在匿名改动区里插入/删除会让对齐漂移，整函数级配对不可靠。
9. **本轮未做**：42 个 dChk>0 函数的逐条重读（时间不足）；AVE 差分只确认了镜像存在，未跑指标。
10. **直答见 §6**：不能。

## §2 指标定义（本轮新增）

对每个函数，统计「**受保护的寄存器索引访问**」：

```
ldr/str/ldrb/strb/... [xN, xM, ...]        ; 寄存器变址访问
  ↑ 在同一函数内、向前 ≤8 条指令里存在
cmp|cmn|subs|sub|adds|tst  +  b.<cond>     ; 且该 b.<cond> 紧跟在比较之后
```

计一次。理由：`improved bounds checking` 的汇编形态就是**在索引访问前多一个比较+条件跳转**；而 `0x2bad` 毒化（`cmp xN, wN, sxtw` + `csel`）是 int32 范围闸，**不计入**（判据 7 仍然有效）。

## §4 手读结果：两个候选都是**配对假象**

### 4.1 第二个（已被证伪）

27.2 的 `0xfffffe0008cb90ec` 是一个 **275 条指令**的完整函数：

```asm
0x8cb90ec  bti c
0x8cb90f0  pacibsp
0x8cb90f4  sub  sp, sp, #0xe0
0x8cb910c  ldrb w8, [x0, #0xb8]
0x8cb9110  tbnz w8, #0, 0x8cb9520
0x8cb911c  adrp x1, 0xfffffe0007443000 ; 一串 bl 0x8cb9568（表初始化，w2=0,1,2,3）
...
```

而配对给出的 27.0.1 对应函数 `0xfffffe0008c096dc` 只有 **3 条指令**：

```asm
0x8c096dc  bti c
0x8c096e0  ldr x0, [x0, #0x20]
0x8c096e4  mov w1, #8
0x8c096e8  b   0xfffffe0008d58eb0
```

**两者毫无关系。** 配对漂移的原因很清楚：difflib 在 4409 vs 4284 个函数的匿名改动区里对齐，一处插入就把后续所有配对位错一格。

### 4.2 第一个

`0x8cd63d4` 与 `0x8c72d90` 的大小差 +849 条，量级上就说明不是「加了一个 `cmp`」——更像又一处位错。**未逐条手读**（时间不足），但按同一机制判为同因。

## §5 卡点（下一轮该换的方法）

**卡点**：`nsyms=0`，函数无名字、无边界元数据，跨版本配对只能靠内容对齐；一旦某个函数体插入了表初始化/日志代码（就像上面那个 +849），对齐就断。

**可用的替代方法**（按成本排序）：

1. **局部签名匹配**（推荐）：不要整函数配对。取 27.2 里每一个「guard + 索引访问」三元组，把其**前 6 条归一化指令**做签名，去 27.0.1 全量函数里搜同一签名；若命中且命中处**没有**这个 guard ⇒ 就是新增的边界检查。这个方法不依赖函数边界，能扛插入。
2. **字符串 xref 定位**：26 个 selector 的 ANE 接口与 AVE 的 13 个 selector 在 census 里有点位；从 dispatch 表 → handler → 新 guard，路径短且不需配对。
3. **调用图层面对齐**：先用 `bl` 图做稳定的锚（入口函数、`__mod_init_func`），再在锚之间局部对齐。

## §6 直答

> **不能。本轮没能定位到这 7 个 CVE 对应的任何一处修复点。**

试了什么、卡在哪：

- 试了：按公告措辞设计「受保护的寄存器索引访问」指标，对 ANE 全量差分（4284 / 4409 函数、158 个改动对），得到 2 个候选，**逐一手读后全部是配对假象**（§4.1 已给出完整反证：27.0.1 侧是 3 条指令的 thunk，27.2 侧是 275 条指令的完整函数）。
- 卡在：**无符号导致跨版本函数配对不可靠**。指标本身能看见 bounds checking（348 → 358 说明它在动），但它比较的是"同名函数"，而"同名"这件事在没有符号时是猜的。
- 未做：① 42 个 dChk>0 函数的逐条重读（`out/S2-ANE-RESULTS.md` 的旧结论因此**仍处于撤回状态，未被新结论替代**）；② AVE 侧指标差分（`ave.27.0.1.macho` / `ave.27.2.ga.macho` 都在，但本轮没跑）；③ IOSurface 竞态路径 —— 需要换缺陷类别，用锁/引用计数差分，不是长度索引。

**一句话**：公告把「找什么」定死了，但**「在两个无符号镜像之间对齐同一个函数」这一步还是断的**；下一步必须先解决对齐，别再用整函数配对。

## §4 归一化配对重做

### 4.0 先纠一个数：函数边界改用 `LC_FUNCTION_STARTS`

上一轮我用「`bti`/`pacibsp` + 前一条是终止指令」的启发式切函数，报 **A=4284 / B=4409**。这一轮改用 `LC_FUNCTION_STARTS`（`cmd=0x26`）解出权威边界：

| 镜像 | `LC_FUNCTION_STARTS` | dataoff / datasize | ULEB 解码后落在 `__TEXT_EXEC` 的函数数 |
|---|---|---|---|
| `ane.27.0.1.macho` | 存在 | `0x1dcc88 / 0x1b08` | **4959** |
| `ane.27.2.macho` | 存在 | `0x1ea5e8 / 0x1bd0` | **5100** |

自证：首项 ULEB 解码值 = `0x17cfe10`，而 `__TEXT_EXEC.vm - __TEXT.vm = 0xfffffe0008c06ee0 - 0xfffffe00074370d0 = 0x17cfe10` —— **完全相等**，故函数起点是相对 imagebase 的偏移。

⇒ 上一轮的 4284/4409 **偏少约 14%**，且边界是猜的。**Δ函数数 = +141**（5100−4959）。

### 4.1 归一化规则（位置相关编码全部抹掉）

| 指令 | 归一化 |
|---|---|
| `adrp xN, #0x...` | `adrp xN, #PAGE` |
| `bl/b/br/blr/braa/blraa #0x...` | 目标 → `#T` |
| `b.cond / cbz / cbnz / tbz / tbnz #0x...` | 目标 → `#T` |
| 其它 `0x...` 操作数 | → `#A` |
| `#imm`（`add/sub/cmp/lsl` 的立即数） | **保留**（判据要用） |

按函数拼接后取 SHA1。

### 4.2 精确配对结果

```
唯一哈希条目      A=2399  B=2444
精确 1:1 配对     1780
未精确配对        A'=3179  B'=3320
```

**为什么只有 1780**：A 的 4959 个函数只对应 2399 个不同哈希 ⇒ 大量函数是**重复形态**（thunk / stub / 相同的 getter），哈希相同的组内多于一个，无法 1:1 认定，被排除。这是方法本身的边界，不是 bug。

### 4.3 剩余集的模糊配对（收紧后）

规则：只在**长度相等的 `replace` 块**内 1:1 配对（长度不等整块拒绝），并要求归一化首 3 条 / 尾 3 条相同，或大小差 ≤3。

```
可靠配对 22 对  |  被锚定拒绝 3724
在这 22 对里，27.2 新增 guard 的函数：0 个
```

**22/6499 的覆盖率太低，所以「0 个」只能读作「在 22 对里没有」，不能读作「ANE 没有新增 guard」。**

### 4.4 便宜的路径先跑了：26 个 selector 的 handler **全都没变**

按你说的「从 census 派发表出发」，取 `com.apple.driver.AppleH16ANEInterface` 的 26 个 selector，逐个对 `handler` 和 `tail` 两个 VA 做「定位函数 → 归一化哈希 → 在 27.2 里找」：

```
selector 相关函数（handler + tail 共 52 个 VA，去重后 50 个不同哈希）
  未变（27.2 里哈希命中）: 50
  变了:                    0
  定位失败:                0
```

**结论：这 26 个 selector 的全部 handler 与 tail，在 27.0.1 与 27.2 之间归一化后逐指令相同。**

⇒ **ANE 的 2 个 OOB write 修复不在 `AppleH16ANEInterface` 的 user-client 方法体里**，也不在它的 tail 里。这条短路径到此关闭 —— 它把「handler 入参校验」这个假设直接否掉了，而不是「没找到」。

修复只可能在更深处：handler 调下去的驱动内部函数（旧方法报的 158 个改动函数就在这一层）。

### 4.5 直答

> **不能。用归一化配对，本轮仍然定位不到 ANE 那 2 个 OOB write 的修复点。**

卡在第 3 步（剩余集配对），具体：

- 第 1 步（归一化）**成功**：位置相关编码已全部抹掉。
- 第 2 步（精确哈希配对）**部分成功**：1780 对，无歧义，但只覆盖 2399 个唯一哈希中的一部分（重复形态函数无法 1:1）。
- 第 3 步（剩余集配对）**失败**：3179 vs 3320 个函数，收紧锚定后只配到 **22 对**，覆盖率 0.3%。根因是 ANE 有 141 个**新增**函数混杂在剩余集里，而新增函数在 27.0.1 里没有对应物，因此不满足「长度相等块」条件，整块被拒。
- 第 4 步无从谈起（22 对上 0 个新增 guard）。

**但换来了一个确定的否定**：26 个 ANE selector 的 handler/tail **全部未变**（§4.4），所以 OOB write 不在这一层。

**下一步最短的路**：以已配对的 22 对 + 1780 对精确配对为锚，取 **27.2 新增的 141 个函数**（在 27.0.1 中无对应物）单独列出 —— 新增函数本身就是强信号，不需要配对就能看；再对它们跑 guard 判据。这条我本轮没做。
