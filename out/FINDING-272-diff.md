# FINDING：IOSurface 27.0.1 → 27.2 差分（注册表生命周期）

> 本文只写**可复核的机械事实**与**明确标注的推断**。没有 27.2 真机，所有 27.2 一侧结论均为静态。

---

## 1. `+0xf1`：新增的「已拆除」粘滞标志

| 版本 | `ldrb/strb [x,* #0xf1]` 字节访问 |
|---|---|
| 27.0.1 | **0 处** |
| 27.2 | **2 处** |

```asm
; 27.2 注册路径（锁内）
0xa394500  ldrb w8,[x21,#0xf1]
           tbz  w8,#0 -> 继续注册
           add  w20,w20,#0x1b           ; -> 0xE00002D8 kIOReturnNotAttached

; 27.2 注销路径 0xa394744（= 27.0.1 #802 对应体）函数最开头
0xa394760  mov  x20,x1                  ; 两参数：x0=root, x1=self
0xa394768  ldr  x0,[x0,#0x150]          ; root 锁
0xa394770  mov  w8,#1
0xa394774  strb w8,[x20,#0xf1]          ; ★ 永久标记
0xa39478c  cmp  [node+0x58],x20         ; 摘 node+0x58 == self 的节点
```

**推断（静态）**：27.2 在拆除 user client 时打永久标记，此后任何注册尝试返回 `0xE00002D8`。
**实测支持**：27.0.1 上「注册 → 注销 → 再注册」三步全 `SUCCESS`（40/40），见 `FINDING-reregister.md`。
**未实测**：27.2 真机上第 4 步返回 `0xE00002D8` 这一条。

## 2. 为什么标志在 `+0xf1` 而不是 `+0xf0`

**更正（原表述有误）**：拆除路径清门用的是 `sturb`（单字节），不是字写。
真正的理由是「`+0xf0` 是可重置的当期门，`+0xf1` 是粘滞位」，而拆除时 `sturb` 只写 `+0xf0` 这一字节，
所以粘滞位必须放在 `+0xf1` 才能不被拆除自身的清门动作擦掉。
另有一条**字写**清零在析构路径（见下），但对象此时已死，不影响判定。

```asm
0xa343764  ldr w21,[x0,#0xf0]     ; 当 count 用
0xa343778  lsl x1,x21,#3          ; 释放 count*8 字节
0xa343790  str wzr,[x19,#0xf0]    ; ★ 整个字清零（含 +0xf1）
```

标志放在 `+0xf1` 才能与计数解耦、活过清零。

## 3. 拆除顺序变化（**本项目静态判定，未经第二方复核**）

| 版本 | 顺序 |
|---|---|
| 27.0.1 | 清 `+0xf0` → `0xa348910` → `0xa3450b0` → **`#802` 摘链（最后）** |
| 27.2 | 清 `+0xf0` → **`#802` 摘链（最前）** → `0xa396cf8` → `0xa393480` |

> 这一条是单方静态阅读结果，**请按未复核处理**。`+0xf1` 的两处字节访问是可独立复核的机械事实。

## 4. `+0x108` / `+0x110` 写侧：不可从用户态供给（负结果）

29 处写入中，去掉栈与清零，真正的整体赋值只有 4 处：

```
0xa346860  str x0,[+0x108]  ; str w26,[+0x110]   ; 扩容：count*2
0xa346a38  str x20,[+0x108] ; str w23,[+0x110]
0xa3509b4  str x0,[+0x108]  ; str w23,[+0x110]   ; 分配 + 赋值
0xa350afc  str x19,[+0x108] ; str w22,[+0x110]   ; 失败回滚
```

- 扩容路径有 `65536` 上限检查（`lsr w8,w23,#0x10 ; cbnz -> fail`），扩容后 `count*2 ≤ 0x1FFFE`，`lsl x1,x26,#3` 用完整 64 位，**无截断**。
- 数组元素是**带 tag 的内核指针**，写入/校验共用同一套 tag 运算（`add x8,x20,x23,lsl#3 ; eor x16,x20,x8 ; tst`，与 `0xa34f8cc` 同源）。

**结论**：写侧不能由用户态直接决定值；要利用它得先有内存破坏原语 —— 循环依赖。**此方向不再投入。**

## 5. 未变的部分（27.0.1 与 27.2 一致）

- 故障链：`0xa3338cc`（释放链遍历）→ `0xa3462f0`（遍历 `root+0x188`）→ `0xa346338` → `0xa34ff88 ldr x0,[x0,#0xd8]`（对已释放的 user client 取锁）。
- `far = x0 + 0xd8`，5 次 panic / 5 个 KASLR slide / 4 个 CPU 完全一致。
- 选择子契约：`sel17` 异步专用、`sel18` 同步专用、`structureInput` 精确 24 字节。
