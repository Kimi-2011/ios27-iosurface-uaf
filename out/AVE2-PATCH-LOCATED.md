## §2 各检查函数校验的字段与上界（手读，27.2）

### 2.1 `AVE_HEVC_CheckVPSExtBounds` `0xfffffe00087c5bb8`，`(x0, x1 = pVPS)`

调用点传 `x1 = ctx + 0x1880` ⇒ **下列偏移全部相对 VPS 结构**：

| 指令 VA | 字段 | 检查 | 上界含义 |
|---|---|---|---|
| `0x87c5be0` | `[VPS+0x04]` | `cmp w8,#0x40; b.hs` | `< 64`（`vps_max_layers_minus1 < 64`）|
| `0x87c5bf4` | `[VPS+0xf78]` + `byte[VPS+0x1a40]` + 1 | `cmp,#0x41; b.hs` | 和 `< 65` |

## §3 VPS 检查的调用点（27.2，手读）

形态完全一致，共 5 处（全部在 `0x87c5xxx`–`0x87c96xx` 区间）：

```asm
mov  w8, #0x1880
add  x1, x21, x8          ; x1 = ctx + 0x1880  = pVPS
mov  x0, x19
bl   0xfffffe00087c5bb8   ; AVE_HEVC_CheckVPSExtBounds
cbz  w0, <成功路径>        ; w0 != 0 → 失败/断言
```

| 调用点 VA | 成功跳转 |
|---|---|
| `0xfffffe00087c520c` | `0xfffffe00087c5748` |
| `0xfffffe00087c6fc0` | `0xfffffe00087c73cc` |
| `0xfffffe00087c7a8c` | `0xfffffe00087c7e9c` |
| `0xfffffe00087c863c` | `0xfffffe00087c8a48` |
| `0xfffffe00087c91c4` | `0xfffffe00087c95d0` |

⇒ 27.0.1 的这些函数里**没有这次 `bl`**，其余指令照旧执行 —— 这就是「补丁之前那段代码」的入口。

## §4 一条被否定的嫌疑：layer-set 数组**不是**落点

按你的提示查 `num_tile_columns_minus1` / layer set 这条线，结果如下。

27.2 的写入者 `0xfffffe000889228c`：

```asm
0x8892284  cmp  w4, #0x3f
0x8892288  b.hi 0x8892500        ; ← 上界检查
0x889228c  add  x22, x13, x1, lsl #6
0x8892290  strb w6, [x22, w4, uxtw]   ; 写
```

27.0.1 的同一逻辑 `0xfffffe0008858124`：

```asm
0x8858128  strb w8, [x19, x10]
0x885812c  add  w10, w10, #1
...
0x8858138  cmp  w8, w10, uxtb
0x885813c  b.hs ...
```

并且 27.0.1 里**同样存在**这三处上界检查（与 27.2 的 `0x889240c` / `0x8892448` / `0x8892458` 一一对应）：

| 27.0.1 | 27.2 | 检查 |
|---|---|---|
| `0x88581e0  cmp w8,#0x3f; b.hi` | `0x889240c` | `≤ 63` |
| `0x885821c  cmp w13,#0x40; b.hi` | `0x8892448` | `≤ 64` |
| `0x885822c  cmp x8,#0x3f; b.hi` | `0x889245c` | `≤ 63` |

**结论：这条路径在 27.0.1 上已经有边界检查，本次补丁没有改它。** `num_tile_columns_minus1 <= 256` 这条嫌疑**降级**（不能排除它在别处，但至少不通过 layer-set 数组越界）。

## §5 卡点与下一轮

**卡在哪**：三个检查函数的**字段表**拿到了，但「哪个消费者在 27.0.1 上缺检查」还需要把**调用点所在函数**逐条对齐——那些函数在 27.2 里加了这次 `bl`，其余指令可能同时有变化，仍需版本对照；而对照又回到配对问题。

**下一轮最短路径**（不用整函数配对）：

1. 取 §3 的 5 个调用点，各取**调用点后 40 条指令**（27.2），归一去 `#T`，在 27.0.1 全量反汇编里做**滑窗精确匹配** —— 命中位置就是 27.0.1 的对应代码，命中位置**往前**看有什么；这段代码在 27.0.1 里没有前置校验。
2. 对命中段里的每个 `str/strb` 寄存器变址写，追索引寄存器的来源，看它是否直接等于 `[pVPS+4]` / `[pVPS+0x1a40]` / `cfg+0x510` 之类的字段。
3. MCTF / LRME 两条线同理，但它们的 `x3` 来自客户端参数块，**用户可控性更容易证**，优先级应高于 VPS。

## §6 直答

> **不能完整给出**「字段 → 计算 → 越界内存操作 → 用户控制方式」这条链。

已确定的半边（手读，可直接用）：

- **用户可控输入的位置**：`AVE_Client_CheckMCTFInfo` / `CheckLRMEInfo` 的 **`x3`** 是客户端提交的配置结构，字段为 u32 计数/枚举（`+0x510 < 8`、`+0x768 < 8`、`+0x1888 ≤ 6`、`+0x27f8 ≤ 15`、`+0x2c10 ≤ 16`）。27.0.1 上这些检查不存在。
- **VPS 侧**：`pVPS = ctx + 0x1880`，校验 `[+0x04] < 64`、`byte[+0x1a40]`、`byte[+0x17fb + i] < 64`、`byte[+0x1a41 + set*64 + k]`；5 个调用点已列全。

未确定的那半边：**具体是哪一次写入越界**。已排除 layer-set 数组（§4）。

**一句话**：锚（新函数 + 调用点）比配对可靠得多，这一轮把「检查什么、谁调用、用户从哪进来」都拿到了；差的最后一步是「调用点之后的消费者在 27.0.1 里长什么样」，用 §5 第 1 条的滑窗匹配可以拿，本轮没做完。
